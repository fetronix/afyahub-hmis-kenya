# Receipt and refund settlement recovery

Date: 2026-11-06. This describes the **local reviewed billing-to-ledger workflow**, not an authenticated M-Pesa callback or an automatic money transfer. The current provider callback is disabled. See the [M-Pesa hardening and Phase 2 gate](../integrations/mpesa-settlement-hardening-2026-11-06.md) for provider-specific limits and test evidence.

## Design and transaction boundaries

1. `recordSettledPayment` records a manual receipt, invoice totals, attribution when supplied, retry identity and minimal audit in one PostgreSQL transaction. `recordManualRefund` likewise records an immutable manual refund and updates the invoice transactionally. A manual M-Pesa reference is a cashier attestation, not authenticated Safaricom evidence. Refunds are manual attestations, not proof that a transfer occurred.
2. **The existing immutable receipt/refund is the durable work item.** The read-only `accounting_payment_settlement_status` view (migration `0069`) derives its accounting state from the existing source, attribution, finalized invoice, reviewed source links, journal and reversal evidence. There is no separate queue or duplicate payment/journal. Every committed source is discoverable even if a process dies before requesting a journal; old unposted sources are also visible without rewriting them. A legacy helper may have created sources without attribution or the modern audit; the view flags missing evidence rather than assuming it.
3. An authorized accountant opens **Receipt and refund settlement work** in Accounting. The list is facility-scoped and cursor-paged, defaults to unresolved work across all dates, and can also show all sources. Account browsing returns active accounts from the selected facility in bounded pages with optional search. No account mapping is guessed or automatically approved. The existing reviewed journal form remains available for invoice postings. Post the finalized invoice first; then receipts and refunds in recorded order.
4. The reviewed retry endpoint uses the source's stable, server-derived key and the existing `postBillingSourceScoped` transaction. The source-linked journal, its balanced lines, source linkage and journal audit commit together; the view then changes atomically. Existing database uniqueness, source ordering, active-account, scope and open-period checks still apply. A failure rolls that transaction back and leaves the source visible. Concurrent exact retries resolve to one journal; changed details after a successful posting conflict rather than repost. After a network-unknown result, refresh the source and retry the exact same details; a delayed request may still finish.
5. Each retry attempt is audited before posting. A failed attempt adds a minimized code-only audit row; the service refuses to start a posting if the attempt audit cannot be written. A crash can occur before failure audit is written, but the committed receipt/refund remains independently discoverable. An audit-write failure after a failed/uncertain attempt is returned as an error, not success. Journal audits are part of their own atomic posting transaction. No automatic worker, automatic account mapping or guaranteed response-time SLA is implemented.

## States and history

These are **derived accounting states**, not claims about external provider authentication. They cannot be directly assigned through an API; they follow persisted evidence. Receipt and refund sources have separate rows in the view.

| State                             | Meaning / next action                                                                                                                                                                                                                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SUCCESS_AWAITING_SETTLEMENT`     | A local receipt or manual refund is recorded and its prerequisites are present, but its reviewed journal is missing. “Success” describes the local record only; it does not mean a provider callback was verified.                                                             |
| `RECONCILIATION_REQUIRED`         | Evidence needs review, e.g. missing attribution/finalization/parent journal, an untracked journal, invalid amount, or a recorded refund whose journal is missing or reversed. Review the accompanying code; do not manufacture or silently replace evidence.                   |
| `SETTLED`                         | The local source has an active, source-linked posted journal and no detected outstanding refund exception. This is an accounting state, not proof of provider settlement.                                                                                                      |
| `PARTIALLY_REFUNDED` / `REFUNDED` | The receipt has recorded manual refunds with active reviewed refund journals totaling less than / equal to its amount. These labels do not prove external transfer of funds. An unposted or reversed refund makes the receipt require reconciliation instead.                  |
| `REVERSED`                        | A posted journal has a posted controlled reversal. The source receipt/refund and both journals remain in history; this is not deletion, a new receipt, or an automatic refund. Reposting that same source is not offered; use an authorized correction/reconciliation process. |

For example, an unattributed receipt can be `RECONCILIATION_REQUIRED`, become `SUCCESS_AWAITING_SETTLEMENT` after the missing evidence is properly supplied, then `SETTLED` after a journal. A later recorded refund temporarily requires review until its own journal is posted; a journal reversal is represented without changing the original receipt. Source/journal dates and audited attempts provide evidence of the sequence; this view is not a separate event-sourcing timeline.

Provider request states are a separate guarded lifecycle: `INITIATING`, `PENDING`, `UNKNOWN`, `FAILED` (including the documented cancellation code `1032`), `PROVIDER_CONFIRMED` (query-reported success only), and `REVIEW_REQUIRED`. Conflicting terminal evidence moves to review, never back to pending/success. The database enforces allowed transitions and immutable request identity, and the service applies the same transition rules to queries. A verified-provider-success-to-receipt state does **not** exist yet; it must not be invented while the authentication contract is missing.

## Authorization and isolation

- `GET /api/accounting/payment-settlements` and `/payment-settlement-accounts` require both `accounting.read` and `billing.read`; retry requires `accounting.journals.post` and `billing.read`. Facility identity comes from authenticated scope, not an unchecked client ID. Platform super-admin status alone does not confer facility-finance permissions. An out-of-scope source is not returned.
- Existing `payment_hub_reconciliations` database and service guards require a same-facility **production** transaction and independently recorded matching receipt; sandbox reconciliation to an operational receipt is refused. Migration `0069` makes a provider integration's environment/ownership and a request's integration/amount/invoice/reference identity immutable so those constraints cannot be bypassed by later rebinding.
- Sandbox initiation and query do not create receipts, change invoices, or post journals; the callback remains 503. There is **no isolated sandbox financial ledger**, and an unrelated manual entry can still be falsely keyed by a human because the system has no authoritative source of a sandbox receipt code. Training and real-provider end-to-end testing therefore require an independently isolated synthetic database/facility and explicit controls; do not use these operational tables as a sandbox ledger.
- No provider event is persisted as verified before receipt creation. A crash after a hypothetical authenticated verification but before a durable verified intent is not recoverable by this feature; that provider-side orchestration remains a release blocker. The code contains no endpoint that asserts a callback was verified.

## Migration and operation

`drizzle/0069_payment_settlement_recovery.sql` adds a receipt/invoice index, the derived view and transition/identity triggers; it does not delete, backfill, reprice or rewrite historic financial rows. The new index and triggers can take locks and the view may require query-plan assessment at production volumes. The finalized migration was applied only to isolated synthetic databases, both as an incremental upgrade and from an empty database, after read-only plans; never reset an existing database. Before any real upgrade, independently verify a backup and restore, review existing request data and trigger compatibility, measure locking/performance, approve a deployment/rollback plan, and perform production change authorization. Inspect migration-status drift warnings: the current status tool can print READY and exit zero even when a recorded migration hash differs. No production migration or restore was performed here.

The read-only view is an operational exception list, not a complete financial audit. Existing untracked journals, inconsistent historic sources and missing attribution require controlled finance review; `SETTLED` is not a substitute for reconciling a bank/M-Pesa statement or for reviewing the approved chart of accounts.
