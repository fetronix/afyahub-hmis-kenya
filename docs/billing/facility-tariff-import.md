# Facility tariff review and batch intake

The facility must supply its own reviewed schedule, codes, units, effective dates and documented approval. These tools do not discover, independently approve, infer or update prices; their availability is not proof of a complete catalogue. The blank [`facility-tariff-intake-template.csv`](facility-tariff-intake-template.csv) is a human worksheet, **not** a CSV importer or a source of approved prices.

## Facility-owned service catalogue transfer

A facility administrator with `tariffs.manage` can use **Facility services → Import / export** to create 1–200 facility services with linked initial tariffs. This is **create-only**: conflicts with any existing service or tariff code, including inactive and unlinked historical tariffs, are rejected instead of overwritten. The finance module and the relevant service department must be enabled. SUPER_ADMIN status alone does not authorize facility finance. Existing master references and invoice snapshots are not changed.

1. Prepare a JSON **array**, not the exported CSV. Each object has `code`, `name`, `description`, `department`, `category`, `unit`, `isActive` and `autoBill`. Optional `initialPrice` defaults to `0.00` KES, which means **unconfigured**, not free care or billable zero; `initialTariffCode` defaults to the service code. Optional `effectiveFrom` and `effectiveTo` are `YYYY-MM-DD` or null. The screen contains a blank structural example; replace it with actual facility-reviewed values. Unknown fields, invalid dates and duplicate or conflicting codes are rejected. Pharmacy dispensing continues to use inventory prices, not this catalogue.
2. Enter or upload the JSON, validate, review **every normalized row**, enter the facility's documented approval reference and confirm the review. The approval reference is an operator attestation; the software does not verify approval. Do not include patient data, passwords or provider credentials in it. Validation does not reserve codes: the final transaction rechecks the facility, modules and conflicts.
3. Prepare the batch. Before sending, securely retain the **exact reviewed request**, approval reference, facility and displayed retry identity under the facility's retention procedures, and attest that you have done so. The application does not silently store that request for later recovery. The batch, linked services/tariffs and their audit entries commit together, or the transaction rolls back.
4. If the response is interrupted, use **Check recorded status** or **Retry same request** without changing the pending identity. After closing or reloading, reopen the transfer panel, enter the original JSON, approval reference and retry identity, and validate. A recorded batch is shown as a match only when the normalized request and approval match. A key belonging to different contents or a legacy import is rejected. If no batch is found, review the rows and retry only the original request with the **same** identity; `NOT_FOUND` is a point-in-time observation, not proof that an earlier in-flight request cannot commit. Do not create a replacement key or assume a failed delivery means failure to commit. Investigate discrepancies with an authorized finance administrator. Previously created records may have changed since the recorded import.
5. **Export catalogue CSV** requires `tariffs.read` and the facility-administrator role. It includes the selected facility's services and linked tariffs, including inactive/archived links; it excludes unlinked historical tariffs and is not a round-trip import file. It represents one read snapshot, protects spreadsheet cells from formula execution and records an export audit before returning data. Above 5,000 joined rows it fails rather than returning a partial export. Keep exports under the facility's approved access and retention controls.

The corresponding scoped, no-store API endpoints are `POST /api/facility-services/import/validate` with `{ facilityId, rows }`, `POST /api/facility-services/import` with `{ facilityId, rows, idempotencyKey, approvalReference, confirmed: true }`, `POST /api/facility-services/import/status` with `{ facilityId, idempotencyKey, rows, approvalReference }`, and `GET /api/facility-services/export?facilityId=…`. The export API returns a JSON envelope containing base64 CSV, filename, content type, row count and coverage. Status can be queried with the key alone, but then `requestMatched` is false and it does **not** establish that the caller's request matches. Same-key, same-normalized-rows and same-approval import replays return the recorded result; different contents conflict. These are synthetic-tested capabilities, not facility UAT or production approval.

## Audit first

A facility administrator with `tariffs.read` can use the tariff validation panel or `GET /api/billing/tariff-validation?facilityId=<facility>&offset=0&limit=200`. Continue with `nextOffset` until it is null; each request uses a fresh, read-only database snapshot, so changes between pages can affect a multi-page review. The facility and finance module must be authorized and enabled.

The report assesses active/unknown-activity laboratory tests, wards, inventory-name proxies and generic charge-family scenarios using the charging resolver. It identifies, among other things, unresolved services, duplicate normalized codes, invalid/missing/non-positive prices or units, inactive/expired rows, incompatible units and conflicting links. It also reports aggregated billed tariff codes or references that are absent from the current facility catalogue. Old billed codes can legitimately be historical snapshots: investigate rather than rewriting old charges.

`RESOLVED` means only that the resolver found a candidate under the checked configuration; it is **not** approval of its price, unit, payer applicability or clinical suitability. Inventory names are proxies, and free-text consultations, procedures, imaging and other services are not an exhaustive catalogue. Findings are not an assertion that a missing service was never provided or that the facility owes a particular amount. The report does not modify records.

## Legacy standalone tariff-only API

1. Obtain the authorized facility's reviewed schedule and documented approval outside this API. Use a facility administrator account with `tariffs.manage` and only the permitted facility; a platform SUPER_ADMIN is not a substitute for a facility financial role. Finance and the relevant department modules must be enabled.
2. Convert **only approved, explicit values** into 1–200 JSON rows. Each row accepts `code`, `description`, `department`, `unit`, `fee`, `shaStatus`, `shaNotes`, `billingKey`, `effectiveFrom`, `effectiveTo`, and `autoBill`; unknown fields are rejected. `code`, `description`, an enabled `department`, `unit`, a positive `fee`, and a boolean `autoBill` are required. `shaStatus` defaults to `Not Assessed` when omitted; it is not a SHA authorization. Optional dates use `YYYY-MM-DD`. A nonempty billing key must be recognized by the existing charge engine. For each automatic link, the facility must review the applicable service, unit and effective dates; do not assume a matching code is correct.
3. Send `POST /api/service-tariffs/import/validate` with `{ "facilityId": <facility>, "rows": [<reviewed rows>] }`. This is a dry-run and returns `valid`, `rowCount` and row-numbered `issues`; it does not write. It checks formatting, explicit price and auto-bill choice, module enablement, normalized duplicates in the batch and conflicts with current facility codes/active billing keys. Validation does not lock the configuration for a later import, so the actual import rechecks.
4. After reviewing all issues, send `POST /api/service-tariffs/import` with the **same reviewed rows**, `facilityId`, a unique `idempotencyKey` (8–128 letters, digits, `.`, `_`, `:`, or `-`), `confirmed: true`, and an `approvalReference` (3–200 characters, no control characters). The key may instead be supplied in the `Idempotency-Key` header. The reference must identify actual documented facility approval; the service merely records the operator's attestation and **cannot independently verify approval**. Do not include patient data or credentials in the reference.
5. A successful new batch returns HTTP 201 and a batch ID, count and created IDs/codes. Same-key, same-normalized-contents and same-approval retries return the recorded result with HTTP 200 and `idempotentReplay: true`; a changed request conflicts. The batch, individual tariff rows and audit records commit in one transaction, or none do. Existing tariffs are not overwritten; resolve conflicts through the facility's controlled review and existing tariff-management workflow.
6. For an ambiguous response, `POST /api/service-tariffs/import/status` with `facilityId` and the original `idempotencyKey` checks for a recorded batch. `NOT_FOUND` is only a point-in-time observation: a delayed request may still arrive. Do not invent a replacement identity or start a second import on that basis; retain the original reviewed request securely and investigate/retry with the same key. This older, tariff-only API is separate from the facility-service catalogue screen and is not recovered through that screen.

Do not put session tokens, facility passwords, provider credentials, actual patient records or unapproved prices into examples, source code, logs, support tickets or the intake worksheet. Use the facility's protected authenticated API tooling and approved retention procedures. The automated tests exercise synthetic prices and codes only; no real facility schedule has been inspected or approved.
