# Facility tariff review and batch intake

This is an **API-only**, facility-scoped intake process. It does not discover, approve, infer or update prices, and it is not proof of a complete service catalogue. The facility must provide its own current, approved prices, units, codes, effective dates, mappings and evidence of approval. The blank [`facility-tariff-intake-template.csv`](facility-tariff-intake-template.csv) is a human worksheet, **not** a CSV importer or a source of approved prices.

## Audit first

A facility administrator with `tariffs.read` can use the tariff validation panel or `GET /api/billing/tariff-validation?facilityId=<facility>&offset=0&limit=200`. Continue with `nextOffset` until it is null; each request uses a fresh, read-only database snapshot, so changes between pages can affect a multi-page review. The facility and finance module must be authorized and enabled.

The report assesses active/unknown-activity laboratory tests, wards, inventory-name proxies and generic charge-family scenarios using the charging resolver. It identifies, among other things, unresolved services, duplicate normalized codes, invalid/missing/non-positive prices or units, inactive/expired rows, incompatible units and conflicting links. It also reports aggregated billed tariff codes or references that are absent from the current facility catalogue. Old billed codes can legitimately be historical snapshots: investigate rather than rewriting old charges.

`RESOLVED` means only that the resolver found a candidate under the checked configuration; it is **not** approval of its price, unit, payer applicability or clinical suitability. Inventory names are proxies, and free-text consultations, procedures, imaging and other services are not an exhaustive catalogue. Findings are not an assertion that a missing service was never provided or that the facility owes a particular amount. The report does not modify records.

## Validate and import

1. Obtain the authorized facility's reviewed schedule and documented approval outside this API. Use a facility administrator account with `tariffs.manage` and only the permitted facility; a platform SUPER_ADMIN is not a substitute for a facility financial role. Finance and the relevant department modules must be enabled.
2. Convert **only approved, explicit values** into 1–200 JSON rows. Each row accepts `code`, `description`, `department`, `unit`, `fee`, `shaStatus`, `shaNotes`, `billingKey`, `effectiveFrom`, `effectiveTo`, and `autoBill`; unknown fields are rejected. `code`, `description`, an enabled `department`, `unit`, a positive `fee`, and a boolean `autoBill` are required. `shaStatus` defaults to `Not Assessed` when omitted; it is not a SHA authorization. Optional dates use `YYYY-MM-DD`. A nonempty billing key must be recognized by the existing charge engine. For each automatic link, the facility must review the applicable service, unit and effective dates; do not assume a matching code is correct.
3. Send `POST /api/service-tariffs/import/validate` with `{ "facilityId": <facility>, "rows": [<reviewed rows>] }`. This is a dry-run and returns `valid`, `rowCount` and row-numbered `issues`; it does not write. It checks formatting, explicit price and auto-bill choice, module enablement, normalized duplicates in the batch and conflicts with current facility codes/active billing keys. Validation does not lock the configuration for a later import, so the actual import rechecks.
4. After reviewing all issues, send `POST /api/service-tariffs/import` with the **same reviewed rows**, `facilityId`, a unique `idempotencyKey` (8–128 letters, digits, `.`, `_`, `:`, or `-`), `confirmed: true`, and an `approvalReference` (3–200 characters, no control characters). The key may instead be supplied in the `Idempotency-Key` header. The reference must identify actual documented facility approval; the service merely records the operator's attestation and **cannot independently verify approval**. Do not include patient data or credentials in the reference.
5. A successful new batch returns HTTP 201 and a batch ID, count and created IDs/codes. Same-key, same-normalized-contents and same-approval retries return the recorded result with HTTP 200 and `idempotentReplay: true`; a changed request conflicts. The batch, individual tariff rows and audit records commit in one transaction, or none do. Existing tariffs are not overwritten; resolve conflicts through the facility's controlled review and existing tariff-management workflow.
6. For an ambiguous response, `POST /api/service-tariffs/import/status` with `facilityId` and the original `idempotencyKey` checks for a recorded batch. `NOT_FOUND` is only a point-in-time observation: a delayed request may still arrive. Do not invent a replacement identity or start a second import on that basis; retain the original reviewed request securely and investigate/retry with the same key. The browser does not yet provide a bulk-import or cross-device recovery UI.

Do not put session tokens, facility passwords, provider credentials, actual patient records or unapproved prices into examples, source code, logs, support tickets or the intake worksheet. Use the facility's protected authenticated API tooling and approved retention procedures. The automated tests exercise synthetic prices and codes only; no real facility schedule has been inspected or approved.
