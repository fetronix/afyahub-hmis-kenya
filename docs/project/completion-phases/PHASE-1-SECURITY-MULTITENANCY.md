## Scope and findings

The detailed source findings and evidence are in [the Phase 1A investigation](../../audits/JALICARE_PHASE_1A_SECURITY_INVESTIGATION.md); the crosswalk is in the [completion register](../JALICARE-COMPLETION-REGISTER.md). There are no PA-04/PA-05 in that document; they have not been invented or silently renumbered.

Progress included in the testing checkpoint:

- Lab overview, list and download require the session patient and order/result patient to match, with tenant/facility and verified-result checks. Originating-facility release policy and classification of clinical notes remain unresolved.
- Patient portal login serializes account updates and revalidates account state/version; patient-initiated password change revalidates the account and requesting session under lock and commits password, session revocation and a static audit record together. This does **not** establish safe forced-reset identity proofing or atomicity of all administrative/recovery paths.
- Sharing create/revoke/redeem is transactional with row locking and static access/audit entries. Text states that the named recipient is **not verified**, that the code is a bearer credential and that redemption returns metadata only. It is not proven persistent record access or an approved release/recipient-verification policy.
- Empty permission lists fail closed. FHIR is gated by the interoperability facility module; the target facility and returned patient are bound, including for tenant/platform users. The interoperability and patient-journey UIs fence stale patient/facility responses and disable stale exports. Switching tenant/facility clears the selected patient and closes the journey modal. These are limited changes, not proof of all clinical association or isolation boundaries.
- Relevant error messages in the changed portal/FHIR paths were made static rather than logging underlying query errors. Global audit/redaction, access-log completeness and proxy/IP trust remain unverified.

## Outstanding critical dependencies and blockers

1. Forced-reset restriction, recovery/identity proofing and all administrative security-state/revocation races; staff must-change API restriction and MFA enrollment/challenge/recovery remain incomplete.
2. Same-tenant cross-facility care/referral/emergency relationship rules are not approved or consistently enforced. Several clinical writes check patient tenant while reads use registration-facility scope. Clinical work that relies on such a relationship cannot be declared safe or complete by frontend filtering.
3. Patient-note classification, originating-facility release rules and consent need named clinical/privacy owner decisions. Raw visit notes remain a release concern. Recipient identity is not verified by sharing codes.
4. Comprehensive authorized and unauthorized isolation for financial, pharmacy, reports/exports, jobs and provider credentials, and atomic/audited/redacted access across all relevant routes, has not been established by the focused tests above.
5. Encryption coverage, legacy plaintext, deployed TLS, key custody and recovery, proxy configuration, independent security testing and facility UAT remain unverified. Do not rotate keys or rewrite legacy records without an approved recovery plan.
6. Historical archives and the old environment file are **deferred, not resolved**. No archive inspection, deletion, history rewriting, credential rotation or incident response was performed.

Phase 2 work may address independent, narrowly scoped clinical capabilities only where the server enforces the necessary tenant, facility, patient, permission and audit boundaries. Remaining Phase 1 work and its eventual completed-phase verification are still required. Phase 3 was separately authorized after this Phase 1 checkpoint; committing work for testing does not resolve these dependencies.
