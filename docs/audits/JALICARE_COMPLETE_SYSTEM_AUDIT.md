## A. Executive summary

JaliCare is a substantial, real application, not just a set of mock screens. It has persisted, scoped clinical workflows; facility-owned pricing; invoicing and manually recorded payments; a reviewed double-entry ledger; staff and patient sessions; limited reporting; integration configuration; and a significant automated test suite. Several safety boundaries are deliberately fail-closed. These strengths do **not** establish that all departments, financial controls, national returns or external integrations are complete, or that a particular installation is safe and approved for clinical use.

## B. Overall assessment, methodology and status definitions

### Scope and evidence limits

Read the current mounted routers and middleware order, UI registry and module components, domain services, schemas and migration journal, integration boundaries, test configuration, prior evidence and CI metadata. The clinical journey and representative mutation, authorization, price, audit, export and error paths were traced across layers. Static inventories parse **485 TS/TSX files** and identify **188 Drizzle `pgTable` declarations** in exported domain schema files. A separate migration text scan identifies **189 distinct literal `CREATE TABLE` names**: `website_booking_reminders` is SQL-only and accessed with raw SQL, not a Drizzle declaration. Neither count proves the shape of a deployed database. The route-call scan is only syntactic and includes false positives and misses dynamically defined routes; no exact live endpoint count is claimed. Mounts are inventoried in Appendix 3.

No real database, patient data, deployment, provider, sandbox account, or production secret was accessed. No schema or application functionality was changed, no migrations were applied, and no provider call was made for this audit. Dependency checks used the npm registry; GitHub was used for repository/CI metadata. Historical reports are supporting evidence, not substitutes for inspection or present production acceptance. Static inspection and selected tests cannot prove that every handler is secure or every facility dataset is valid.

**Status applies to the named feature and stated boundary, not the product as a whole:**

- **FULLY IMPLEMENTED AND VERIFIED** — only for a narrowly specified behaviour actually verified at the stated test level, never shorthand for clinical/provider/production acceptance. Example: the simulated no-write migration dry-run check in I.
- **IMPLEMENTED BUT NOT FULLY VERIFIED** — the indicated local UI/API/persistence path exists, with material testing, operational, facility or acceptance evidence missing.
- **PARTIALLY IMPLEMENTED** — some real steps exist, but a requested lifecycle, source, financial linkage, verification, or output is missing.
- **FRONTEND ONLY** — the identified feature is represented in UI but the named saving/clinical capability is not implemented; a UI that reads other real data does not make that feature complete.
- **BACKEND ONLY** — a named API/service exists without a corresponding mounted end-user workflow established here. A database table alone is not a backend implementation.
- **MOCKED / SIMULATED ONLY** — observed evidence concerns mocks or labelled simulation, not the provider or a real facility.
- **NOT IMPLEMENTED** — the named capability has no implemented route/engine/workflow established in the inspected scope. A similarly named table or menu is not sufficient.
- **BLOCKED BY EXTERNAL PROVIDER** — the operation needs an authoritative contract, authorization, credentials or external acceptance not available in this audit; local scaffolding may still exist.
- **PRODUCTION BLOCKER** — an unresolved condition that prevents an appropriate production release for the affected scope. This can coexist with another status.

For compact references below, `U/` means `src/components/modules/`, `R/` means `src/routes/`, `S/` means `src/db/schema/`, `T/` means `src/tests/`, and `M` means the numbered `drizzle/` SQL migrations. A test path identifies relevant source, not a claim that its DB cases ran in the fresh no-DB audit. Appendix 2 lists all declarations and migration names. Cross-cutting permissions/scoping come from `src/auth/authorization.middleware.ts`, `src/auth/scope.service.ts`, `src/middleware/facility-module.middleware.ts` and `src/seeds/permissions.ts`; test examples include `T/authorization.spec.ts`, `T/route-scope.spec.ts` and `T/vitest/tenant-isolation.db.spec.ts`.

### System and relationship model

React/Vite UI and `src/api/` clients call an Express server (`server.ts`, `src/app.ts`) with PostgreSQL/Drizzle (`src/db/`). `src/App.tsx` and `src/config/facility-modules.ts` determine visible modules; a visible/hidden menu is not an authorization decision. Server-side session, permissions, tenant/facility scope and module guards are separate. `src/db/schema/relations-{tenancy-auth,clinical,operations}.ts` and table foreign keys express parts of the relationship model: tenant → facility → staff/roles, patient ↔ facility → encounters/appointments/observations/orders, encounter/admission → performed care → invoice/item/receipt/refund, reviewed billing source → journal/lines → chart/period, and bank statement → matched journal/payment. Many historical/nullable IDs, free-text fields, migrations and raw SQL require separate scope and integrity review; a foreign key alone does not prove that all related rows have the same tenant/facility.

`src/app.ts` mounts auth and health first; portal activation/login and authenticated portal/admin routers, SHA/ payment webhooks and client-key website booking have their own pre-staff-gate controls. Staff routes then pass `requireAuth` and `requireAuthorization` before module and domain routers. Publicly mounted does **not** mean every handler is unauthenticated, and placement before the staff gate does **not** prove each alternative authentication mechanism is sufficient. More detail and representative routes are in Appendix 3.

### C.1 End-to-end patient and financial trace

1. **Identity → attendance:** an authorized staff member registers/selects a real facility patient, creates or checks in an appointment, and moves through a scoped queue. Website requests use a separate client-key API and require staff identity and shared-diary review before confirmation; they are not automatically a completed encounter or payment.
2. **Triage → care:** observations and encounter notes/diagnoses are saved against scoped patient/encounter identities. OPD can request lab/imaging and prescribe. Orders and prescriptions are not themselves proof of completion or dispensing. Specialty notes and full theatre clinical care remain disconnected; dialysis session completion does not auto-bill.
3. **Completion → charge:** consultation completion, verified lab work, imaging report, completed procedure, documented delivery, actual dispensing and inpatient bed evidence can lead to charge attempts using explicit facility service/tariff identity, dates and snapshots. Missing/invalid configuration can leave work unbilled rather than blocking care or inventing a price. Historical sources without identity must not be backfilled by guessing. Pharmacy uses actual dispensed quantity and inventory selling price; bed policy uses configured ward default/bed override and immutable evidence, with review on missing data. See `src/billing/facility-charge-resolver.ts`, `src/billing/charge-attempts.ts`, `src/inventory/inventory.service.ts`, `src/inpatient/bed-billing.service.ts`.
4. **Invoice → receipt/refund:** invoice lines and totals are persisted; finalization records a reviewed responsibility split, not external insurer authorization. Manually recorded receipts are not necessarily independently bank-confirmed. Refund records describe a manual action, not an electronic transfer. Item-level adjustment/credit-note lifecycle and comprehensive outstanding AR are missing.
5. **Discharge → accounting/reporting:** discharge is a clinical commit, not proof that every charge succeeded; it marks the bed for cleaning and creates durable bed-billing work. Reviewed source posting creates balanced, source-linked journals separately; source and journal cannot be assumed atomic. Report Centre uses a limited set of scoped, declared snapshots and ledger movements, not a comprehensive verified accounting close or statutory submission.

### H.2 Authentication, application and operations

- Staff session tokens are hashed server-side but bearer values are stored in browser `localStorage` (`src/api/clients/http.ts`); patient portal tokens use `src/api/portal-client.ts`. This creates exposure if script execution/XSS or an unsafe extension/device compromises the origin; it is not proof of an XSS exploit. Evaluate secure HttpOnly cookies, CSRF/session policy and device controls with a threat model.
- `src/auth/auth.service.ts` deliberately withholds a staff session when MFA is required, and `src/auth/auth.controller.ts` states the MFA challenge endpoint is not implemented. This is fail-closed, but MFA-required users cannot complete login. Staff and portal have per-account lockout and IP limiters; `express-rate-limit` has no configured shared store, so process-local limits do not provide a distributed ceiling. Review proxy trust and multi-instance controls.
- `src/middleware/http-security.middleware.ts` supplies Helmet, production CSP/HSTS and an origin allowlist; `src/app.ts` limits request bodies and logs paths without query strings/bodies. Actual TLS termination, proxy trust, CORS, monitoring, CSP effectiveness, WAF and deployed settings were not tested. `SQL_SSL` defaults to false; certificate verification defaults true **only if TLS is enabled** (`src/config/env.ts`).
- Backups are removed from the current tracked tree, but four historical archive additions remain reachable in the fetched Git history; GitHub reports the repository as public. Coordinate containment and history cleanup with the repository/data owners; preserve authorized incident evidence, assess copies/forks/caches and rotate relevant credentials. Determine notification obligations with counsel/DPO based on actual facts; no unauthorized access or specific data contents were investigated here.
- `Dockerfile`, `docker-compose.yml`, `README.md` and `docs/deployment/` document non-root packaging, migration/preflight, logging and recovery practices. No live environment, load, availability, patching, independent restore, monitoring or rollback was tested. The pool maximum is 10 (`src/db/index.ts`); provider timeouts/network calls and concurrent workloads need load testing. The client build produces a ~2.5 MB minified JS chunk and a size warning.
