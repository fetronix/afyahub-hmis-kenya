## Safety and compatibility notes

- This release deliberately disables the old free-text `POST /api/theatre-cases` and `PUT /api/theatre-cases/:id` writes after validation/scope checks; they return `LEGACY_THEATRE_WRITE_DISABLED`. Integrations relying on those writes must be assessed and migrated before deployment. The historical `GET` remains available but now requires **both** `theatre.read` and `clinical.read` because it exposes old clinical notes/checklist data. The new schedule response does not expose those notes, checklist JSON or idempotency values.
- New Theatre APIs require an authenticated, authorized, facility-scoped user and an enabled Theatre module. `theatre.read` covers schedule/rooms/practitioners/history; `theatre.rooms.manage` controls rooms; `theatre.schedule.create` creates bookings; `theatre.schedule.manage` moves/cancels; `theatre.schedule.reconcile` records or revokes legacy reviews; `theatre.reports.read` reads the aggregate report. The UI also requires `patients.read` for patient search. Permissions must be deliberately seeded and delegated to appropriate facility roles; they are not automatically granted to `SUPER_ADMIN` by the seed. Confirm actual assignments and clinical responsibilities with facility administrators.
- Legacy review reasons and scheduling reasons are visible to authorized schedule readers; enter only the minimum scheduling explanation, not detailed clinical notes. A mistaken legacy attestation can result in a conflict with an external or old reservation; the software cannot independently verify a manual review. Review all cases and external schedules, not just old status values.
- Exclusions protect structured reservations using half-open `[start,end)` intervals and permit adjacent slots. They do not check other team members or external booking systems. When a room enters maintenance, existing reservations are not automatically moved or cancelled. The facility must review them.
- Migration `0031_theatre_scheduling.sql` is additive and does not backfill legacy cases. It uses built-in PostgreSQL range GiST operators, not `btree_gist`; it also adds a unique index to the existing case table. DDL can lock tables, and the migration intentionally stops if same-named unjournaled objects exist. Some constraints are expressed in SQL rather than fully in Drizzle schema metadata: future schema generation must preserve them. A transactionally rolled-back synthetic-schema test checked legacy-row preservation and conflict constraints; a fresh synthetic database applied the complete chain. This is not evidence about an existing facility's data or migration runtime.
- Before any deployment: take and verify backups; review the target migration journal, locks and data with a DBA; dry-run and plan only the pending changes; reconcile legacy reservations and integrations; seed/delegate least-privilege roles; approve local procedures and validate in a facility-approved non-production environment. **Do not replay the historical chain on an existing database:** historical migration `0002` contains destructive statements and was authorized here only for new isolated synthetic databases. No production migration or deployment was performed.

## Synthetic acceptance evidence and missing journeys

- PostgreSQL integration tests cover authentication/module/permission checks, facility isolation, room states, invalid inputs, patient/practitioner scope, concurrent identical requests, concurrent overlapping requests, room/patient/practitioner conflicts, adjacency, cancellation rollback, revision conflicts, audit/history, elective/urgent/emergency labels, legacy-write refusal and explicit reversible legacy review. An encounter/admission booking leaves the synthetic admission admitted and does not bill it.
- A transactionally isolated migration test retains a synthetic historical case and checks the exclusion and composite patient constraints. UI tests exercise empty inputs, retry keys, loading/error states, scoped facility switching, reporting, history and explicit legacy acknowledgement.
- The full consent/checklist refusal, stock-shortage, billing-failure, interrupted clinical documentation and finalized-amendment journeys **cannot be demonstrated** because the underlying Theatre clinical, stock and billing workflows are not implemented. Existing tests do not substitute for those requested acceptance scenarios. Tests establish software behavior for this partial increment, not patient safety or clinical approval.
