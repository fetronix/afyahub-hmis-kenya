## Implemented in this increment — still work in progress

### Staff appointment scope and lifecycle

- Replaced the unsafe unscoped staff query/write with `src/appointments/appointments.service.ts` and `src/routes/appointments.routes.ts`. The server resolves the facility against the authenticated context and derives the persisted tenant from that facility. Facility-level users cannot select another facility; tenant-level users must select one. The patient must belong to the tenant and be registered at, actively related to, or have an encounter at the selected facility, matching the existing patient-access policy. Optional department and practitioner must be active at that facility; an active practitioner flag **is not credential verification**. Supplied actor/record IDs are not accepted, a mismatching tenant is rejected, and a new staff appointment can only start as `Scheduled`.
- Validates actual calendar date and local wall time (`YYYY-MM-DD HH:mm` or `YYYY-MM-DDTHH:mm`, optional seconds; no guessed timezone offset), duration, IDs and explicit priority. Missing type or priority remains unrecorded rather than being treated as a clinical finding. The existing duration default remains 30 minutes. Existing nonconforming historical time strings are not rewritten.
- New staff-created records receive a random booking reference and authenticated creation user, an optional facility category and service-identity snapshot. Mapping a category to a service does **not** create a price, charge, invoice, payment or proof of clinical care. Staff-created `CREATED`, `CHECKED_IN`, `CANCELLED`, `RESCHEDULED_FROM` and `RESCHEDULED_TO` events are append-only and retain actor, previous/new status, reason when applicable, related appointment, time and queue identifiers. An audit row is written in the same transaction. The event payment field is explicitly `NOT_ASSESSED`; it does not assert a balance, refund, payer decision or transfer.
- Create accepts an optional `Idempotency-Key` for compatibility with existing clients; new reception submits one and keeps it on retry. Concurrent same-key/same-payload requests by the same actor and facility return one appointment; reuse for different payload returns 409. Older clients that omit a key **do not** receive a retry guarantee. Rescheduling requires the key and atomically retains the old `Rescheduled` record and one linked replacement; a key replay returns the same replacement. Cancellation requires a reason and does not delete or refund. Both actions are limited to scheduled/confirmed, not-yet-checked-in standalone appointments.
- Check-in requires an explicitly selected queue station and creates the queue token and appointment transition in one transaction. Repeated and concurrent check-in of an appointment is refused; same-patient/station check-ins through this new path serialize. The `BK-{appointment id}` token is deterministic and checked for an existing token. **The older generic queue writer does not share the lock or a global token uniqueness constraint**, so cross-path token/active-queue races remain a blocker. A check-in is not treatment or billing. Cancellation/rescheduling after check-in is refused until queue reconciliation is implemented.
- Generic staff actions refuse dialysis- or website-linked appointments rather than leave source records inconsistent. Source workflows still have independent status changes; the new event ledger is **not a complete history of all historical, website or dialysis actions**. No historical actor, reference, category, payment state or event was inferred or backfilled.

### Dialysis cancellation

`POST /api/dialysis/schedules/:id/cancel` requires both `dialysis.schedule.manage` and `appointments.cancel`, a reason, and an authenticated facility scope. It locks the schedule against concurrent session start, accepts only `SCHEDULED` slots with no session, rejects website-linked or inconsistent linked appointments, and atomically records `CANCELLED`, the reason, the linked appointment cancellation/event and both audit entries. A synthetic failure of the schedule audit rolled back both records and the event. It does not cancel, undo or infer an actual session, charge, refund or payment. Existing unlinked legacy schedules can be cancelled without inventing an appointment event. Dialysis rescheduling, arrival coordination, recurrence, chairs, broader cross-channel capacity, billing and laboratory linkage remain open.

### Page, API and permissions

- `ReceptionQueueModule.tsx` embeds `AppointmentDiary.tsx` and `AppointmentCategoryManager.tsx`. Staff can search the existing facility-scoped patient list, navigate to existing patient registration, choose an active category, department/practitioner and priority, enter local time, duration, reason and notes, and create a booking. Patient search returns at most 50 results. No category, service, provider or treatment is invented; category setup uses a facility-approved code/name and may reference an existing active facility service ID. The UI can add, activate and deactivate categories; the API also supports editing their name/service mapping. The new configuration permission must be seeded and explicitly delegated; this work has not seeded any real deployment.
- The diary is a **paged, date-filtered list**, not a complete interactive calendar. Day/week/month views, patient-ID/category/practitioner/status filters, explicit inclusion of inactive records, and history/actions are available. Counts are **per loaded page**, not facility totals. Active filtering includes only `Scheduled`, `Confirmed` and `Checked-in`; unknown legacy states are visible only with history included. There is no global name/MRN diary search, resource availability proof, or payment screen. The UI labels payment as unlinked/unassessed and warns that availability is not shared across channels. It displays errors rather than treating them as zero or success. On facility/timezone changes the reception and dialysis views remount to avoid showing a previous facility's cached records or unsaved form data.
- `GET /api/appointments` (`appointments.read`) supports selected facility, date range up to 366 days, active/status, patient, category, practitioner, `limit` (maximum 200) and `offset`. It returns at most 50 by default. `POST /api/appointments` requires `appointments.create`. `GET /api/appointments/resources`, `/categories` and `/:id/history` require `appointments.read`. `POST /api/appointments/categories` and `PATCH /api/appointments/categories/:id` require new `appointments.categories.manage`. `POST /api/appointments/:id/cancel` requires `appointments.cancel`; `/:id/reschedule` and `/:id/check-in` require both `appointments.update` and `appointments.create`. All staff appointment paths remain behind the `reception` facility-module gate; dialysis paths remain behind the `dialysis` gate. Backend authorization and facility checks are authoritative.
- `drizzle/0064_staff_appointment_lifecycle.sql` and `drizzle/meta/_journal.json` add nullable appointment reference/category/service/actor/priority/replacement/queue columns and indexes, plus `appointment_categories`, `appointment_events`, `appointment_requests`, scoped foreign keys and the append-only history trigger. `src/db/schema/clinical.ts` and `src/db/schema/appointment-booking.ts` describe the new fields. Migration does not backfill existing records. It has **not** been deployed. Production migration and permission seeding require a separately approved backup, review, release plan and UAT.

### How staff would use this work after authorized deployment and training

1. In **Appointments & Queue**, select the correct facility. An authorized category manager adds approved category names/codes, optionally entering an existing active facility-service ID; verify the service separately. This does not configure prices.
2. Use **Book Appointment**, search and explicitly select the patient, category or type, local date/time, optional practitioner/department/priority, and reason/notes. Confirm availability manually across relevant diaries; the success notice does not mean an SMS or payment occurred.
3. Use the date and day/week/month controls, filters and pagination in the diary. Include history to see cancelled/rescheduled records; use **History** to inspect recorded events. For standalone scheduled records, choose an explicit check-in station or provide a reason for cancellation/rescheduling. Review payment separately in the existing authorized billing workflow; no refund is automatic.
4. For a not-yet-started dialysis slot, authorized staff may use **Cancel schedule** in the dialysis unit and provide a reason. Website-linked, already-started, checked-in or inconsistent cases require an appropriate separate review; do not mark them complete or alter finance by inference.
