# Hospital service and billing discovery audit

**Source snapshot:** `b198db105442f24f84663a02bf53df9145803eb2` (current main at audit start); audit prepared on 31 October 2026. This is a **repository audit, not a facility or production audit**. No facility database, real patient, tariff schedule, payer contract, live provider, or deployed migration state was inspected. No clinical, billing or configuration data was changed.

## Executive conclusion

The repository contains real but partial clinical, tariff and invoice paths. It does **not** provide enough information to enumerate every service a particular facility actually offers or bills: lab tests, inventory, wards, prices and payer mappings are facility data, while procedure and imaging names can be free text. Missing information means **unknown**, not “absent”, “not covered” or “free”. A source-level match is not approval of a clinical service, fee or payer code.

The inventory contains **180 explicitly classified rows**: 156 named service identities, 19 schedule-dose identities, and five clearly marked product classes that must be expanded into individual items after authorized facility discovery. It includes source-defined entries, panel components, examples and explicitly labelled validation candidates. These counts are **not counts of services implemented, offered, chargeable or configured**. A generic order path may accept a name without a dedicated specialty workflow or actual catalogue entry.

The most consequential findings are:

1. **Generic procedures can appear completed and be charged at creation.** The schema defaults status to `Completed` and `performedAt` to now; the API attempts a charge after insertion without checking status. This is a source finding, not evidence that an actual patient was incorrectly recorded or charged. [Schema](../../../src/db/schema/clinical.ts#L302), [scoped insert](../../../src/db/queries/clinical.ts#L233), [route](../../../src/routes/diagnoses.routes.ts#L124).
2. **Special-ward pricing can fall through to a generic bed tariff.** Synthetic checks reproduce both the generic `BED_DAY` alias and `BED-DAY` code pricing an ICU/HDU night after the resolver skips the family-wide _link_. A specific ward-ID link takes precedence on the original attempt, but the queued retry reconstruction loses that ID; actual facility configuration is unknown. [Resolver](../../../src/billing/tariff-resolver.ts#L484), [candidate codes](../../../src/billing/tariff-matching.ts#L767), [retry reconstruction](../../../src/billing/charge-attempts.ts#L579).
3. **Tariff timing and identity need hardening.** Delayed bed-day accrual uses the server's current calendar date for tariff resolution, not each occupied date; the manual invoice API checks `isActive` but not effective dates. Synthetic tests also reproduce row-order-dependent selection for case-variant codes/keys and an exact lab code resolving a pharmacy-department tariff. [Accrual](../../../src/db/queries/inpatient.ts#L758), [resolution call](../../../src/billing/billing.service.ts#L469), [manual invoice](../../../src/routes/domains/invoices.routes.ts#L53).
4. **Dialysis and theatre do not have demonstrated patient-charge flows.** Dialysis completion explicitly returns `UNBILLED`; its consumable path records stock/cost rather than a patient invoice. Theatre has scheduling, not a demonstrated operation/anaesthesia completion and billing path. [Dialysis](../../../src/dialysis/dialysis.service.ts#L743), [theatre](../../../src/routes/theatre-scheduling.routes.ts#L151).
5. **Many requested specialties are absent, screen-only, or shared-flow only.** The specialty screen expressly says it cannot save specialty-specific notes, prescriptions or charges. Neonatal details remain linked to maternal delivery without a baby patient ID in `delivery_babies`. Immunisation records exist but no dose charge trigger was found. [Specialty screen](../../../src/components/modules/SpecialtyModule.tsx#L10), [newborn schema](../../../src/db/schema/maternity.ts#L362), [immunisation route](../../../src/routes/maternal-health.routes.ts#L659).

No source-only audit can establish a complete clinical-to-invoice department for an actual facility. The department report distinguishes partial workflows from screens, examples, requirements and nonexistent dedicated paths; it does not call a department absent from the physical hospital.

`audit_id` is a report join key, **not** a clinical, billing or payer code. `NAMED_SERVICE`, `SCHEDULE_VARIANT` and `PRODUCT_CLASS_NEEDS_EXPANSION` describe row granularity; the five product classes are not individual stock records. `AUDIT_CANDIDATE` and `REQUIREMENT_OR_AUDIT_CANDIDATE` are questions for facility validation, not discovered facility offerings. `NAMED_PANEL_COMPONENT` records a named component, **not a separate catalogue item or an extra charge**. `AUTOMATIC_ATTEMPT` means only that a particular source event reaches the billing engine, subject to configuration and errors. `GENERIC_PATH_ONLY` means a shared API can record an appropriately entered generic event, not that a named service, specialty workflow or catalogue item exists. `NOT_DEDICATED` means no dedicated path was found in the inspected source; it does not mean that care is unavailable offline or at a facility.

## What is actually traceable to invoices

For wired events, the common path is **UI → scoped/permissioned route → clinical persistence → `chargeAndRecord` → resolver → open invoice and `billing_items` → recalculation/audit**. Resolution requires a suitable facility tariff. A failed/missing price can yield an unpriced attempt or a manual-reconciliation response; check the returned result and queue rather than assuming an invoice line exists. The charge service locks and deduplicates by source identity, but this is not proof that separate source events, manual lines, bundles, cancellations or different catalogues cannot double bill. [Charge attempts](../../../src/billing/charge-attempts.ts#L318), [invoice creation and reconciliation](../../../src/billing/billing.service.ts#L730).

| Family / source            | Trigger actually wired                                             | Limitation                                                                                                                                               |
| -------------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CONSULTATION`             | Non-`INPATIENT` encounter creation.                                | OPD UI submits `Outpatient`; first visit, review, emergency and specialist subtype are not separately identified there.                                  |
| `LABORATORY` / `LAB_ORDER` | Each single or batch lab order.                                    | Ordering is not proof of a performed test; collection/processing are not separately auto-billed.                                                         |
| `RADIOLOGY`                | Imaging order creation.                                            | Study name is free text; an order is not proof of imaging or report.                                                                                     |
| `PROCEDURE`                | Generic `POST /api/procedures`.                                    | No procedure-entry UI was found in the inspected OPD module; defaults and unguarded charging are a safety concern, not a complete specialty workflow.    |
| `ADMISSION`                | Admission creation.                                                | Separate one-off event from bed days.                                                                                                                    |
| `BED_DAY`                  | Accrual during discharge, transfer or explicit authorized accrual. | One idempotency suffix per admission/date; ward identity rather than bed subtype determines tariff candidates. Current code includes the discharge date. |
| `DELIVERY` / `MATERNITY`   | Delivery record.                                                   | Once per delivery on the maternal patient with `encounterId: null`, not per baby. No independent neonatal charge follows.                                |
| `PHARMACY`                 | Dispensing, with quantity and medication name.                     | Stock/dispensation is recorded separately; billing uses a drug name, not the inventory item code as canonical identity.                                  |

See [service traces](SERVICE_TRACES.csv) for exact methods, endpoints, permissions and paths. Patient registration, ANC, labour/partograph, postnatal contacts, immunisation administration, vital observations, dialysis completion, dialysis consumable use and theatre scheduling have **no corresponding dedicated automatic charge trigger found**. This does not make them free.

A separate permissioned `POST /api/invoices` supports manual creation when finance is enabled and the facility/patient are in scope. For a selected tariff, stored tariff values are used; **legacy lines without `tariffId` can use caller-provided descriptions and prices**. A client method exists, but no production UI caller for `createInvoice` was found. This API is not proof of a performed service, an approved price or a specialty-specific workflow; it can bypass canonical service-event deduplication. [Manual API](../../../src/routes/domains/invoices.routes.ts#L53), [legacy item handling](../../../src/routes/domains/invoices.routes.ts#L258).

Specific-ID link validation is meaningful for laboratory tests and ward-specific bed days in the current charge paths. Other families frequently use generic/name-based identities; a link record alone does not prove their actual event passes a matching ID. Normal individual tariff input normalizes code case, and batch import checks normalized conflicts, but historical/direct-writer case variants remain possible. Active billing-key uniqueness is on the **stored exact key**, without effective-date ranges; tariff-code uniqueness is also exact. Consequently, current constraints do not by themselves resolve all normalized duplicates or permit a full same-key schedule of overlapping/adjacent versions. [Schema](../../../src/db/schema/billing.ts#L36), [billing-key index](../../../drizzle/0019_service_tariff_billing_key.sql#L42), [import checks](../../../src/billing/tariff-import.service.ts#L65).

Tariff departments accepted by the write helper do not include standalone `maternity` or `dialysis`; the delivery resolver permits `inpatient`/`specialty` description matching. Do not invent department codes to work around that mismatch. The individual tariff validator permits zero, whereas automatic resolution rejects non-positive fees; bulk intake requires a positive fee and explicit `autoBill`. An explicitly funded or waived service is not equivalent to a missing price, and must be handled under an approved policy rather than silently converted to zero. [Tariff validation](../../../src/routes/shared/tariffs.ts#L19), [department matching](../../../src/billing/tariff-matching.ts#L126), [batch intake](../../../src/billing/tariff-import.service.ts#L21).

## SHA and private insurance boundary

A local service, a facility tariff, a patient's policy, a payer service code, a contracted reimbursement and a claim/payment are distinct facts. Existing `payer_service_code_mappings` is facility/payer scoped and stores local and payer identifiers, dates and reimbursement-related fields, but **no actual mapping was inspected**. SHA format/combination constants in source and `SANDBOX_SIMULATION` benefit examples are software artifacts, not official validated codes, provider benefits or real outcomes. [Mapping schema](../../../src/db/schema/insurance-payers.ts#L223), [SHA constants](../../../src/integrations/sha/sha.fhir.ts#L1), [mock benefits](../../../src/integrations/sha/sha.benefits.ts#L1).

For each real facility, verify the current authorized SHA/DHA interface and each private contract separately: patient eligibility, benefit coverage, preauthorization, referral, supporting clinical documentation, service-specific coding, tariffs, effective dates, submission, acceptance, remittance and payment. A manual check, estimate, local mapping, HTTP acknowledgement or prepared claim establishes none of the later steps. No real claim, production request, external integration or provider response was tested here. Do not put patient data, credentials, payer secrets, real prices or claims into the repository or audit output.

## Facility-validation procedure (not performed)

1. Obtain authorization from the specific facility and tenant, designate clinical/finance/payer data stewards, and use least-privileged, audited access. Keep patient records and provider credentials out of reports and logs. Do not modify or reset any database.
2. Inventory the actual active/unknown-activity **lab tests**, stock items/batches, wards/beds, service tariffs and links, facility module settings and payer mappings from the existing platform; obtain approved local lists for imaging, procedures, packages, contracted services and specialties that are free text or external. A historic order name is a lead for review, not proof of a current offering or performed event. Expand the five product classes and unknown catalogues into one facility-specific row per real identity; remove or mark candidates that do not apply.
3. With an authorized facility admin holding `tariffs.read`, run the existing **read-only** Configuration → tariff validation panel (or its facility-scoped `GET /api/billing/tariff-validation`); page through all results and retain the report only under facility policy. Its database transaction is repeatable-read/read-only. Review duplicate normalized codes/keys, links, missing/inactive/expired/manual-only rows, units, generic and family fallback, ward subtype, inventory proxy names and historical billed-code warnings. [Route](../../../src/routes/domains/billing-analytics.routes.ts#L51), [read-only query](../../../src/billing/tariff-validation.service.ts#L238).
4. Independently reconcile each actual service, ordered/performed event, responsible department, specimen, package membership, stock product, time/unit, locally approved amount and payer contract. Compare exact/normalized codes, family links and aliases; explicitly test the synthetic special-ward and wrong-department cases against proposed configurations. A `RESOLVED` status is not sign-off. Review pending/unpriced attempts and any manual legacy lines with authorized staff; do not infer that queue absence proves no missing charge.
5. Agree policy for cancellations, shared specimens and panels, twins/newborns, bed transfer/discharge days, medication strengths/quantities, dialysis consumables, theatre/anaesthesia, equipment, donor products and public-funded services. Two orders may legitimately share one specimen/accession; do not impose per-order uniqueness or silently reconcile historic conflicts. Do not assume a service or component is patient-chargeable solely because it is listed here.
6. Independently approve clinical workflow, scope/permissions, effective dates, contract versions and payer mappings. Test with a **new isolated synthetic** facility and non-real data, including missing/inactive/zero/future/expired/ambiguous prices, replay, cancellation, cross-source duplicates, cross-tenant access, package inclusion, historical service dates and concurrent writes. A green synthetic test is not facility or provider approval.
7. For any change to posted billing or journals use the existing authorized adjustment/reversal and audit process, respecting closed periods; never silently edit/delete past clinical records or posted financial transactions. Deployment/migrations need a separate backup, explicit migration plan and authorization. Only after facility sign-off and, where applicable, documented provider sandbox verification should the configuration be activated.

A JSON batch tariff validate/import API exists and enforces explicit `autoBill`, positive fee and conflict checks; it does not generate or approve a facility's schedule. The blank intake worksheet is not an actual facility tariff. Do not import the example identities or this audit as live prices. [Batch API](../../../src/routes/service-tariffs.routes.ts#L93).

## Recommended extensible architecture

Extend the **existing single HMIS**, not a second patient, inventory, invoice, accounting or claims system:

1. **Canonical service identity:** maintain a versioned cross-reference to the existing owner catalogue: laboratory tests and panels, radiology studies, procedure definitions, consultation types, ward/accommodation categories, maternity/dose events and inventory products. Specimen type, schedule dose, stock batch, service event, tariff, payer code and facility are related but separate records. The same crossmatch, renal tests, medicines and beds are referenced across departments rather than copied into dialysis, ICU or blood-bank catalogues. Preserve existing IDs and provide reviewed aliases rather than automatically merging uncertain records.
2. **Facility activation and tariffs:** an explicit facility/service/variant activation with permissions, approved effective dates, unit, funding/billability and versioned tariff links; module enablement is not service approval. Model clinic, health-centre, nursing-home, maternity and hospital configurations independently, with no assumed specialty or fee. Preserve facility/tenant boundaries and immutable snapshots on past financial transactions.
