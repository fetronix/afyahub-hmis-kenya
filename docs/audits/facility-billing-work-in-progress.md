# Facility-based billing: work-in-progress status

This is a development checkpoint, **not a release or deployment approval**. The complete database-required suite does not yet pass. Do not deploy or apply these migrations to production on the strength of this checkpoint.

## Architecture and retained history

The active configuration screen and router use facility-owned services and directly attached facility tariffs. The obsolete Master Tariff Price List component and its unused client methods have been removed, and the master catalogue, sync, service mappings, automatic master tariff generation, approval and legacy tariff-management routes are not mounted. The facility manager hides historical master-only tariffs without a facility service, but keeps tariffs that are already attached to a direct service visible because they may still be used for billing. Historical server-side code, database tables, references and financial records remain; the migrations do not copy or infer historical service selections. Existing invoice, payment, receipt, refund, reversal, ledger and audit records are not deliberately deleted or rewritten.

The service and tariff APIs enforce authenticated facility/tenant scope and facility tariff-management permissions. A service's code is unique within its facility, not globally. Tariffs may be archived without deleting referenced historical invoice lines. The invoice engine still stores a price and source snapshot. Missing, inactive, out-of-date, zero-priced, ambiguous or otherwise invalid configurations do not produce a charge. Clinical work can continue when a price is missing; existing charge attempts and their API remain intact, but the review and retry panel is no longer mounted in the facility manager. Pending attempts are not automatically resolved or billed by hiding that panel, and there is no replacement review interface in this change.

The services and tariffs are presented in searchable, horizontally scrollable tables showing the stored price strings, dates, statuses and available actions. New services require an explicitly selected category and billing unit. An open form blocks other mutations, and conflicting edits retain the entered values until the user cancels or explicitly reloads. If a response is lost or otherwise uncertain, the screen requires a reload and verification before another mutation rather than assuming the save failed. The server compares the service's editable `expectedState` and the tariff's `expectedRevision` while holding the relevant row locks; successful tariff edits record full before/after audit snapshots. **API compatibility:** these fields are now required on the respective PUT requests, and older API clients will receive a 400 response until updated. Release the compatible frontend and server together. The separate status PATCH endpoints do not yet have equivalent stale-state protection.

## Clinical connection

- OPD starts without a compulsory consultation-selection modal. An explicitly selected consultation, or the sole active consultation at creation, is persisted; otherwise billing requires review. The consultation is charged on completion, not start.
- The restored OPD investigation workflow retains individual specimen choices for multiple investigations. Laboratory billing uses the investigation's explicitly configured facility service/tariff and occurs after verified completion, not order placement. Free-text/unpriced orders remain clinical records.
- Imaging uses a selected facility examination and charges at reporting. Pharmacy, completed procedures, admissions, occupied bed days and deliveries use the existing invoice engine, with the direct service or exact configured source code as appropriate.
- New admissions persist their selected service identity at creation; existing admissions are deliberately left unselected rather than retrospectively guessed. Encounter request keys use a versioned input fingerprint so retries do not resolve a new service after a catalogue change. Previously stored request hashes are not rewritten.

## Known limitations and required follow-up

1. Procedure insertion and billing are separate; retrying a procedure creation request can create a second clinical source ID. A durable, idempotent procedure-creation/billing workflow requires further design and real database concurrency testing.
2. A delivery currently has no encounter reference in its schema; its invoice can therefore have a null encounter association. Its API concurrency behavior has been tested, but the delivery UI has not.
3. Historical admission and other records without an explicit direct service require controlled review; do not infer or silently backfill selections or prices. Historical master links and financial snapshots must remain intact.
4. The complete database-required suite still needs to pass, with migration verification from a brand-new isolated database, cashier/payment browser exercise, and sanitized browser console/network/server-log review. The inpatient, delivery, procedure and other departmental workflows also need broader real UI and concurrency validation.
5. Permanent deletion does not explicitly check non-foreign-key semantic references in `billing_charge_attempts`; concurrent creation of code-only clinical references can race the existing checks. Do not assume comprehensive reference safety or deploy this destructive operation until these gaps are resolved and tested.
6. Service and tariff status PATCHes are not guarded by the PUT preconditions; stale concurrent status changes can still be overwritten. Deletion has the additional semantic and concurrency gaps described above. Resolve and test those races before release.
7. The hidden charge-attempt panel has no replacement in the manager. Pending records and retry APIs still exist, but operators need an authorized, controlled review path before relying on this workflow; hiding a pending item does not resolve it.
8. No production migration, merge, deployment, live claims/payment, real facility price import or clinical acceptance has been performed. Facility and clinical owners must review configured prices, units, effective dates, completed-service triggers and workflows before any release.
