# Reporting Centre functionality audit — pre-change

**Date:** 4 November 2026. **Starting commit:** bad644c. This is the audit before the current functionality-completion phase; later changes and verification must be recorded separately. It covers every one of the 144 existing catalogue entries, not just the seven menu categories. Candidate tables are evidence of possible source data, not a claim that a finished report or integration exists. The [original baseline](reporting-centre-baseline-2026-11-04.md) and [previous WIP matrix](reporting-centre-wip-matrix-2026-11-04.md) give detailed dependencies.

## How to interpret the display states

- **Unavailable:** catalogue entry has no generator or document workflow. This is missing implementation/dependency, not proof the current user lacks permission. The API returns 404 for unknown engine IDs.
- **Limited view:** an engine exists but implements only the explicitly described subset. It must not be treated as the full requested report.
- **No data:** a successful generated result has a real count of zero; an empty later page after deletion is separately identified. Database/API errors are errors, not empty datasets.
- **Permission required / module unavailable:** a logged-in facility account, selected authorized facility, `reports.read`, enabled analytics and the relevant source module/permissions are independently checked; `reports.export` is also required for print/export. Platform SUPER_ADMIN is not granted facility data. Backend repeats the checks and audits patient access. Account-specific denial is not an implementation status for all users.
- **API error:** validation, scope, module, database or audit failures are returned as errors; no fallback sample data is generated.

Current shared implementation: `src/components/modules/report-centre/ReportCentre.tsx` and `ReportWorkbench.tsx`; router `src/routes/domains/report-centre.routes.ts`; service `src/reporting/report-centre.service.ts`; PDF/XLSX `src/reporting/report-centre.export.ts`. All identified report-centre queries use parameterized predicates, one facility and repeatable-read snapshot. Currently only count is a general summary; no fabricated cross-unit or financial total is supplied. Dates/filters supported are listed in the engine definitions; unsupported filters are rejected, not ignored.

Permission status is **per user and facility**: this audit cannot claim a specific user is RESTRICTED BY PERMISSIONS without their authenticated role and selected facility. Rows classify the implementation itself. `BLOCKED BY MISSING MODULE` is used only where the required payroll/leave/attendance module is absent; missing approvals, mappings, official specifications or external reconciliation are described rather than mislabeled as an absent module.

## Repository-wide placeholder investigation

The tracked repository was searched case-insensitively for `Unavailable`, `Limited View`, `Coming Soon`, `Not Implemented`, `placeholder`, `mock report` and `sample figures`, excluding generated dependencies/builds and the lockfile. In report-centre production code, the unavailable/limited labels are explicit capability states; the input `placeholder` attributes are examples, not data. Existing analytics `unavailable` text distinguishes failed/missing data from zero. Synthetic mocks occur in tests, not in report responses. Other matches include historic audit documentation, configuration guidance, unrelated integration/provider failures, unconfigured tariff records and UI field hints: these are not all reporting placeholders and removing them would hide real safety boundaries. Representative matches were inspected by source and meaning; individual occurrences in unrelated modules were not exhaustively verified. No `mock report` or `sample figures` tracked literal was found. Dynamic/demo figures can require semantic review beyond a text search.
