# PDF static-content compatibility and security investigation

## Scope and diagnosis

Branch: `arena/e088f11d-afyahub-hmis-kenya`

Starting commit: `e754a858e6ac3b54ed7f98f874b7e3cb244fd6d3`

**No failing customer PDF was supplied. The exact feature in the customer's file remains unverified.** This change fixes independently reproduced validator defects, not a guessed diagnosis of an unseen document. No production database or patient/facility documents were accessed.

The exact wording **“Active content, actions and embedded attachments are not supported.”** came from the patient upload validator, `src/documents/patient-file-validation.ts`. Its old parsed-dictionary blacklist rejected every `/A` and `/OpenAction` key regardless of the dictionary's meaning. This was not a MIME, browser-rendering, storage, or sanitization error.

Synthetic PDFs reproduce these specific false positives with the old rule:

| Synthetic file       | Parsed location rejected by old rule | Actual meaning                                                    |
| -------------------- | ------------------------------------ | ----------------------------------------------------------------- |
| `type3-glyph-A`      | `8 0 R/CharProcs/A`                  | Printable Type3 glyph named A; value is a content stream          |
| `tagged-layout-A`    | `9 0 R/A`                            | `/Type /StructElem` layout attributes, `/O /Layout`               |
| `initial-view-fit`   | `2 0 R/OpenAction`                   | Explicit local page `/Fit` destination array, not executable code |
| `static-annotations` | `11 0 R/AP/N/A`                      | Static stamp appearance state A; value is an appearance stream    |
| `local-navigation`   | `2 0 R/OpenAction`                   | Local `/GoTo` with an explicit, validated page destination        |

Ordinary synthetic text, scanned letterhead, images, scanned signatures and vector graphics **did not** trigger the old rule. Merely containing a logo or scanned signature is not an established cause. The new tests retain this distinction.

The facility letterhead endpoint had a **separate** `pdf-lib` parser/geometry validator, not this patient blacklist. Consequently, the historical generic message is not proof of a facility-letterhead validator failure. Its actual failure would need the file and the endpoint/error code. Both upload surfaces now use the same structural active-content policy; letterhead security is strengthened rather than disabled.

## Traced data flow

- Patient UI: `PatientDocumentsPanel.tsx` → `src/api/patient-documents.client.ts` → authenticated raw `POST /api/patient-documents/patients/:patientId`, with encoded metadata header.
- Patient service: checks tenant/facility/patient and metadata, invokes `validatePatientFile` **before insertion**, stores original bytes in `patient_signed_documents.original_bytes` and SHA-256 in `sha256`. The original retrieval endpoint rechecks scope and returns those bytes. Browser preview fetches authenticated bytes into a Blob and displays its object URL in the existing iframe.
- Branding UI: `BrandingDocumentsPanel.tsx` → `branding.client.ts` → authenticated raw `POST /api/facility-branding/facilities/:facilityId/letterheads`. `uploadLetterhead` invokes `inspectLetterheadPdf` before layout measurement, hashing and insertion. `facility_letterheads.source_pdf` and `source_pdf_sha256` retain the original. Upload creates an inactive **DRAFT**, never activation.
- Libraries: `pdf-lib 1.17.1` parses PDF objects; existing `pdf2json 3.2.2` measures letterhead layout; `sharp 0.35.5` validates/decodes image uploads. No application library or lockfile changes. Frontend clients display safe server feature messages, not parser stacks.
- There is no application PDF sanitizer or normalization pipeline in either original-upload path. Letterhead **Preview on a document** is the existing generated-document feature, distinct from **Preview file**. This change does not alter that renderer or substitute generated bytes for originals.

## Implemented policy

`src/security/pdf-static-content.ts` inspects parsed indirect objects, references, arrays and stream dictionaries, including objects from object streams and unreferenced parsed objects. It recognizes dictionary namespaces instead of globally trusting or rejecting `/A`. Collection traversal fails closed at depth 128 / 100,000 visited objects. These are structural inspection bounds, not pre-parser decompression quotas.

### Supported, subject to existing PDF/MIME/size/page constraints

- Printable text, embedded raster images, scans, signature **artwork**, vector graphics, logos, headers/footers, and static Form XObjects (not AcroForms).
- Type3 glyph maps only when every value is a stream; the stream dictionaries remain inspected.
- Tagged structure `/A` attributes with the required attribute owner shape; nested dictionaries remain inspected.
- Static annotation subtypes: Text, FreeText, Line, Square, Circle, Polygon, PolyLine, Highlight, Underline, Squiggly, StrikeOut, Stamp, Caret, Ink and Popup. Link annotations may use validated local destinations only. No external hyperlink actions.
- Annotation appearance maps with only N/R/D appearance entries, and stream-valued state maps. A state named A is not an action.
- Explicit local page destination arrays with recognized view types and validated parameters. A local GoTo action is allowed **only** with Type/S/D keys and a destination referencing a page in this PDF. No action chains. Named destinations are not newly supported.
- Empty inert AcroForm dictionaries without signature flags; nonempty interactive forms are not supported.

### Rejected

- JavaScript, including hex-escaped PDF names and additional actions; Launch actions.
- Embedded attachments of any kind, file specifications, associated files and collections/portfolios; not just `.exe` attachments.
- External URI/remote/embedded-file navigation actions, external stream data, OPI, and external Form references.
- Nonempty AcroForms, widgets, XFA and unsupported form/signature-field interactivity. This is **not** new support for cryptographically signed interactive PDFs.
- Unsupported annotations, multimedia/3D, executable PostScript XObjects, unknown or chained actions, malformed/dangling/unsupported object structures and destinations.
- Existing mismatched MIME/extensions, corrupt/truncated/empty PDFs, unsupported page geometry, oversize uploads and encryption restrictions remain enforced. Patient PDFs retain the 1–100 page limit; letterheads retain their existing first-page portrait/A4-compatible geometry policy and fixed 8 MiB cap. Patient upload limit remains configurable, default 8 MiB.

Feature errors use constant, user-facing messages, e.g. “PDF contains JavaScript actions”, “PDF contains Launch actions”, “PDF contains embedded attachments or file specifications”, or “PDF contains unsupported interactive form elements”, with static-export guidance. Patient `UNSAFE_PDF` remains the active-content error code; letterheads use `LETTERHEAD_UNSAFE_CONTENT`. Unexpected parser details are not returned. The patient raw-body 413 response now also includes a comprehensible size-limit message without changing its existing code/status.

## Originals, preview and consent

- **No normalization, flattening, stripping or rewriting is performed.** The static compatibility defects can be addressed structurally, avoiding the signature/provenance risks of rewriting a signed original. Unsupported files fail closed; trusted static re-export is an explicit user decision, not a silent server conversion.
- Byte equality and SHA-256 are checked against actual stored and retrieved originals on **both** APIs. No new storage system, migration or duplicated document repository was added.
- Patient preview now explicitly says it shows the unchanged uploaded original, not a normalized copy or proof of signature authenticity. Existing browser-viewer/download fallback remains.
- Original file responses retain private/no-store and nosniff. Letterhead original-file responses now also include a restrictive sandbox CSP, matching the defensive patient-file response. Blob previews still depend on the browser's PDF implementation; response headers are not claimed to be a universal PDF sandbox.
- Upload does not assert signatures, verify consent, release to the portal, or activate a letterhead. Patient/doctor signatures remain UNKNOWN; signing date stays null; portal release remains explicit and per-version.
- Original versioning, correction reasons/audit, procedure-specific consent association, separate authorized verification and patient-own portal rules are unchanged. A manual signature scan is neither verified consent nor a cryptographically authenticated e-signature.

### Actual built browser acceptance

`pdf-compatibility-acceptance.ts` runs the built SPA and Express server with the attested PostgreSQL database and controlled Chromium. **99 checks**: 42 UI uploads across both surfaces, every supported PDF's actual authenticated preview Blob checked byte-for-byte (24 previews), visible feature-specific rejections, original hashes and old-rule diagnostics, and no uncaught staff-app errors / same-origin 500 responses. No HTTP mocks/interception or permission bypasses.

The synthetic records persona gets only its existing patient permissions plus branding read/manage and the existing facility-profile UI entry permission; it is not made a wildcard administrator. File selection and existing UI handlers perform the uploads. For branding, enabled-button DOM clicks avoid headless popup-focus loss; they do not synthesize backend requests or replace application handlers. The test observes actual `URL.createObjectURL` Blobs without altering their bytes or weakening CSP.

The existing built-browser simple-upload/consent/portal acceptance is rerun separately, with **36 checks**, including separate signature review/version, verification, correction invalidation, cancelled/wrong-patient rejection, and deliberate patient-own per-version portal release. Its historical evidence/report is not overwritten; new results are included here as `consent-regression-results.json`.

### Visual inspection and limits

This controlled headless Chromium can open the app preview but does not provide a reliable native PDF viewer (blob popups can become downloads). Therefore **iframe existence alone is not claimed as proof of rendered contents**. The authenticated preview Blobs are verified unchanged for all 24 previews. Four of those retrieved synthetic originals are additionally rasterized using isolated test-only **PyMuPDF 1.26.6**, without executing PDF actions or changing the PDFs:

- [Scanned letterhead](pdf-compatibility-evidence/rendered-scanned-letterhead.png): logo, facility heading, header rule, body line, footer rule/text, portrait placement intact.
- [Scanned signature](pdf-compatibility-evidence/rendered-scanned-signature.png): signature strokes and explanatory text intact.
- [Static annotations](pdf-compatibility-evidence/rendered-static-annotations.png): note icon, highlight, ink strokes and teal stamp appearance intact.
- [Type3 glyph](pdf-compatibility-evidence/rendered-type3-glyph-A.png): custom printable glyph artwork and heading intact.

These raster images were visually inspected. This is independent render evidence for synthetic originals, **not** an application-generated replacement preview, customer-file verification, cryptographic signature validation, or a guarantee about all external PDF viewers. No rejected active PDF is opened in a viewer. The application validator is structural inspection, not an antivirus or a complete PDF specification validator.
