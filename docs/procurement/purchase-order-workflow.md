# Procurement and purchase-order workflow

This document describes the implementation added after the earlier audit snapshot. A PO is an internal purchase order, not a point-of-sale transaction. The code and migration have **not** been deployed or applied to a production database by this change.

## Permissions and scope

The procurement module must be enabled for the selected facility. Requests require an authenticated account, the permission below and server-checked tenant/facility scope. Supplier records are **tenant-wide** and shared by the organisation's facilities; a supplier edit/deactivation affects all of them. Orders and their history are facility-scoped. A platform-only `SUPER_ADMIN` account is not a facility procurement account.

| Permission                                     | Allowed operation                                                                                                      |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `procurement.read`                             | List suppliers and orders and read order details and history.                                                          |
| `procurement.create`                           | Create a supplier or a pending order; the existing API also allows a supplier to be created atomically with the order. |
| `procurement.update` plus `procurement.read`   | Edit supplier details/reactivate a supplier; edit an itemized pending order.                                           |
| `procurement.delete` plus `procurement.read`   | Deactivate a supplier or cancel a pending order, with a reason. This is **not** physical deletion.                     |
| `procurement.approve` plus `procurement.read`  | Approve an itemized pending order with an active supplier.                                                             |
| `procurement.reject` plus `procurement.read`   | Reject a pending order with a reason.                                                                                  |
| `procurement.complete` plus `procurement.read` | Record administrative completion of an approved order, with a note and explicit confirmation.                          |

The UI needs `procurement.read` to load suppliers and orders even if create is granted. The API retains the previous `procurement.create`-only creation behavior for compatible existing clients. Grant each operational permission deliberately: the catalogue is not itself a role assignment. Under the existing authorization model, facility-scoped users receive their facility's role override when one exists; tenant-wide users use their role's shared permissions rather than a selected facility's override. Use the existing **Facility Role Permissions** controls to review and grant permissions for facility-scoped users and roles; changing a role affects its assigned users.

For newly provisioned tenants, the default `INVENTORY_OFFICER` catalogue includes read/create/update (not approval, rejection, completion or deletion); the new tenant `FACILITY_ADMIN` default includes read/approve/reject/complete. Existing roles and facility overrides are not silently topped up by this feature's permission seed. The seed adds the permission definitions but does not automatically grant these new actions to existing facility roles, and does not grant procurement mutations to platform SUPER_ADMIN. Existing historical grants are not revoked; platform-only accounts are still refused by procurement routes. Review separation of duties and explicitly assign the permissions needed in each existing facility.

## Form and calculation

The UI records a PO number, existing or newly entered supplier, purpose, expected delivery date, delivery address, payment terms, notes, and 1–100 lines with item description, quantity, unit and quoted unit price in KES. It also records **explicitly entered** tax, shipping and discount amounts; the form starts these adjustments at zero, not an assumed rate or fee. Enter the values from the actual quotation or agreement. No product, price, supplier verification, tax rate or receipt is inferred. Quantities allow three decimal places and monetary inputs two. Each quantity × unit price is rounded half-up to the nearest cent; the server sums the rounded lines, adds entered tax and shipping and subtracts the entered discount. The server validates inputs and computes the stored total instead of trusting a client-supplied total. Discounts cannot exceed the pre-discount total.

Older API clients can still submit a valid amount-only order; it is labelled as lacking item detail. Historical orders and their totals are preserved with no invented lines. A pending amount-only order must be edited to add the **actual** lines before it can be approved. For legacy orders where the creating user was not recorded, the system cannot enforce that historical portion of separation of duties; verify it manually before approval.

## Lifecycle and retention

- New orders start **Pending Approval**; a client cannot set an approver or pre-approve the order. The requester identity is taken from the authenticated session.
- A pending order can be edited, rejected, cancelled or approved by an appropriately permitted user. A user who created **or edited** an order cannot approve it. Rejected and cancelled orders are terminal; create a new order if needed.
- An approved order can be administratively **Completed**. Approval and completion are internal workflow labels. They do **not** prove physical receipt, inventory movement, supplier invoice creation, supplier verification, payment, or external approval. There is no goods-receipt, stock-posting, supplier-payment, or electronic supplier integration in this workflow.
- Only pending orders can be edited or cancelled. Edits, rejection and cancellation are refused if an existing supplier invoice references the order. Such records require separate authorised accounting review; this workflow does not provide invoice resolution or unlinking. No order, supplier, invoice, or historical line is hard-deleted. The PO number remains globally unique, including on cancelled orders.
- Edits and status transitions require the last-seen `revision`. Row locks and revision checks reject stale or racing changes with a conflict. Previous line versions and previous header values are retained; order events and transactional audit entries record actors and actions. Supplier edits/deactivations also write audit entries. A failure to write the audit entry rolls back the operation. Historical orders do not gain fabricated events.

## API and deployment notes

`GET /api/suppliers`, `POST /api/suppliers`, `PUT /api/suppliers/:id`, and `DELETE /api/suppliers/:id` operate on tenant suppliers through a checked facility. `GET /api/purchase-orders`, `GET /api/purchase-orders/:id`, `POST /api/purchase-orders`, `PUT /api/purchase-orders/:id`, `POST /api/purchase-orders/:id/approve`, `/reject`, `/complete`, and `DELETE /api/purchase-orders/:id` provide the order operations. Mutations supply `facilityId`; updates and actions also supply `expectedRevision`. Rejection/cancellation/completion require `note`; completion requires `confirmAdministrativeCompletion: true`. A `DELETE` records cancellation or deactivation only. `409` conflicts require re-reading the record before retrying. New itemized submissions should send line data and explicit adjustments, not rely on a client-calculated total.

Before an authorised deployment, take and verify an appropriate backup, inspect the target's migration status, and review the complete migration plan. Migration `0030_procurement_workflow` is additive; it adds optional header details, revisions, line history and workflow events, without rewriting old orders. Do not replay older destructive migrations or use a force-replay against a real database. Follow the project's approved change process; for example, inspect `npm run db:migrate:dry` and `npm run db:seed:permissions -- --dry-run`, apply only the reviewed pending migration(s), seed the permission catalogue, and deliberately assign facility permissions. Existing facility overrides are not changed by the seed. Test the workflow and separation of duties with synthetic records before granting live access. No deployment or production migration is asserted here.
