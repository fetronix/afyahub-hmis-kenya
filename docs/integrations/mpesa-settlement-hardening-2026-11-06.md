# M-Pesa settlement hardening and Phase 2 gate

Date: 2026-11-06. Branch: `arena/e088f11d-afyahub-hmis-kenya`. This report supersedes the earlier [Phase 1 verification snapshot](mpesa-phase-1-readiness-2026-11-06.md) where this hardening changes the local implementation.

## Decision

**NOT READY FOR PHASE 2. Phase 1 M-Pesa is not complete or production-ready.** The local receipt-to-journal crash gap is now durably visible and recoverable by an authorized finance operator, but no authenticated provider callback or verified provider-to-receipt pipeline exists. No real Safaricom transaction, payment, callback or external transfer was tested. The callback remains disabled (503), including in production. Synthetic manual receipts and mocked queries are not Safaricom evidence.

The [accounting architecture and recovery runbook](../accounting/payment-settlement-recovery-2026-11-06.md) explains transaction boundaries, source-derived status, permissions, retry, history, environment limits and migration precautions.

## Safaricom evidence and exact dependencies

Inspected official sources: [M-Pesa Express Query](https://developer.safaricom.co.ke/apis/MpesaExpressQuery), [M-Pesa Express Simulate](https://developer.safaricom.co.ke/apis/MpesaExpressSimulate), [Authorization](https://developer.safaricom.co.ke/apis/Authorization), and the [Daraja catalogue](https://developer.safaricom.co.ke/apis). The accessible Query documentation describes the sandbox query endpoint, request fields `BusinessShortCode`, `Password`, `Timestamp`, `CheckoutRequestID`, and response fields including `ResponseCode`, `MerchantRequestID`, `CheckoutRequestID`, `ResultCode` and descriptions. It distinguishes request acceptance from result processing, gives result `0` as successful processing and `1032` as user cancellation. Its example does **not** provide amount, currency or a receipt reference, and a query ID match alone does not authenticate arbitrary callback metadata. The previously accessible Simulate sample included amount, receipt, transaction date and phone metadata; the current public fetch yielded generic portal content, so the current complete callback schema, optionality, authenticity and currency contract remain unconfirmed. This is a limitation of available evidence, not proof that Safaricom has no security mechanism. The accessible Authorization page documents Basic client-credentials token issuance and Bearer API calls; its FAQ also states that requesting a new token invalidates the previous token. The current sandbox adapter requests a fresh token for each operation, without coordination across simultaneous calls or application instances, so concurrent token requests may invalidate an in-flight call if that FAQ applies. Confirm the current contract with Safaricom and implement/test scoped token coordination before relying on concurrent requests; unknown dispatch outcomes must not be blindly resent.

Before enabling any financial callback, obtain and independently review:

1. The current official/contractual authentication and integrity mechanism for this exact M-Pesa Express callback, including network/TLS requirements, rotation, origin, acknowledgements, retry/replay policy and incident handling. Do not substitute undocumented headers, shared secrets, IP lists or checkout-ID correlation for provider authentication.
2. Facility-authorized Daraja sandbox app access, relevant product/shortcode and till configuration, credentials/passkeys and test customer/phone access, supplied securely outside Git, logs, chat and PostgreSQL plaintext. Confirm Pay Bill versus Buy Goods fields with Safaricom. Set up explicitly isolated sandbox financial data and policies before allowing any synthetic receipt.
3. The authoritative success/failure/cancellation/reversal callback and/or verification response schema; exact receipt/reference, minor-unit precision, currency semantics, transaction date, phone handling, account reference, correlation IDs and which fields are independently verified by which API. Obtain provider-supported validation of amount, currency, receipt and facility ownership; do not infer missing fields from the query sample.
4. A durable, idempotent verified-event/intention → receipt → reviewed ledger design that validates same tenant/facility, original invoice and amount/currency; records invalid, duplicate and conflicting events without secrets; survives every commit/response boundary; and never replays an uncertain provider dispatch blindly. Add database-enforced source provenance and true sandbox-ledger separation so sandbox evidence cannot create operational receipts or income.
5. An approved facility chart of accounts, mapping, posting and closed-period policies, a reconciliation/exception SLA, refund and reversal authority, production network/security review and incident plan, verified backup/key recovery and restore, provider onboarding/production approval and real facility UAT.

Then run real authorized sandbox tests for success, failure, cancellation, duplicates/replay, amount/currency/reference/ownership mismatches, invalid authentication, cross-facility access, event/receipt/journal interruption and refund/reversal; retain redacted provider evidence. If a provider cannot support a requirement, keep the feature disabled and agree a documented alternative instead of fabricating results.

## Reproducing local synthetic checks

Use only a pre-authorized, isolated synthetic PostgreSQL database whose name includes `synthetic` and `test`; inject connection settings securely, and do not reset an existing database. The full DB test suite uses `JALICARE_REQUIRE_DB=1 npx vitest run --maxWorkers=1`. After client and server builds, the guarded browser smoke is `BROWSER_SMOKE_SYNTHETIC=YES CHROME_EXECUTABLE_PATH=<local-chromium> node scripts/payment-settlement-browser-synthetic.mjs`; it also requires Puppeteer-compatible Chromium, OpenSSL, local browser libraries and the synthetic DB connection environment. The script creates additive synthetic fixtures, uses a short-lived self-signed local TLS proxy and never calls a provider. It is not suitable for production data or a real network verification.
