# Sandbox-ready development strategy — implementation report

Date: 2026-11-06. Branch: `arena/e088f11d-afyahub-hmis-kenya`. Scope: development and synthetic testing only; no production deployment, real patient data, real provider credential, live bank transaction or real provider sandbox call was used.

## Decision and readiness

**The financial integration programme is not sandbox-journey complete or production ready.** The new bank work provides **KCB BUNI and Equity/Jenga sandbox authentication tests only**. This is useful work that can be exercised with facility-authorized sandbox credentials after platform configuration, but authentication is not account access, settlement, a transaction, callback verification or reconciliation. Real provider testing may reveal issues requiring additional development.

Public evidence available here does not establish complete, facility-authorized contracts for all requested providers. Consequently **“add credentials and finish every sandbox journey without another development sprint” cannot honestly be guaranteed**. Unknown contracts remain explicit fail-closed interfaces, not fabricated implementations. The user's instruction to work on bank and insurer integrations in parallel supersedes the historical “do not start Phase 2” sequencing in the earlier M-Pesa report; it does not remove that report's safety blockers.

## Phased work

1. **Baseline and local financial recovery:** the earlier [M-Pesa settlement hardening](mpesa-settlement-hardening-2026-11-06.md) and [receipt/refund recovery design](../accounting/payment-settlement-recovery-2026-11-06.md) establish local safeguards, not external payment verification. The receipt/refund and ledger journal are separate database transactions: committed sources remain discoverable in a durable derived work queue, and authorized reviewed retries are idempotent. There is no automatic verified callback-to-receipt orchestrator or automatic accounting mapping.
2. **Independent bank development now:** BUNI and Jenga sandbox authentication are implemented against the public contracts below. No bank statement, transfer, payment initiation, callback, account-access check or provider transaction was invented. NCBA is explicitly blocked.
3. **Independent insurer/SHA boundaries now:** Britam, PACIS and Jubilee direct adapters fail closed. Misleading legacy Britam/PACIS onboarding assertions were replaced with requests for insurer-confirmed requirements without changing historical runtime settings. The SHA bridge no longer implies process-global settings verify a facility or that SHA, DHA HIE and AfyaLink are interchangeable. Direct electronic insurer and facility SHA transports need further implementation once approved contracts are available.
4. **Next implementation after external clarification:** implement provider-specific operations, authenticated callbacks or provider-approved alternative verification, durable idempotent provider event handling, environment-isolated financial evidence, approved accounting mappings, reconciliation and complete service-to-database journeys. Review safe multi-instance Daraja token coordination and uncertain dispatch handling before concurrent use. Perform separately authorized real sandbox tests and facility UAT. Production approval, security review, restore drills, monitoring and change authorization remain separate gates.

## Bank authentication contract and operational setup

- KCB uses `POST https://uat.buni.kcbgroup.com/token`, HTTP Basic with consumer key and secret, and form `grant_type=client_credentials` as described in [BUNI Getting Started](https://buni.kcbgroup.com/getting-started). The code requires a nonempty access token but immediately discards it; it is not persisted, returned or used for financial operations.
- Equity uses `POST https://uat.finserve.africa/authentication/api/v3/authenticate/merchant`, the documented `Api-Key` header and JSON `merchantCode`/`consumerSecret` according to the [Jenga Developer Quickstart](https://developer.jengahq.io/guides/get-started/developer-quickstart). The access token is immediately discarded.
- Both hosts and paths are fixed in code, HTTPS-only, sandbox-only, with an 8-second abort, bounded response parsing, generic secret-safe errors and **no automatic retry**. The returned `VERIFIED` status is explicitly limited to sandbox authentication. Connection errors, malformed responses, HTTP failures, expired/revoked credentials and configuration changes during a test fail closed. A successful test cannot enable an unsupported financial capability.
- KCB client IDs with the Basic separator and credentials containing control characters, surrounding whitespace, non-ASCII or more than 512 characters are rejected rather than silently altered. The client secret may contain a colon. If an authorized provider issues a format outside these limits, contract review and code changes are required before testing; do not edit the credential to make it fit.
- `HEALTH` is **opt-in**: a platform administrator must explicitly allow the provider/capability and assign it to the facility. A facility administrator with the relevant permission configures sandbox, selects `HEALTH`, enters the provider-specific credentials and runs **Test sandbox authentication**. Activation also requires the existing masked account and current validated credential/configuration checks. The bank's account is not contacted, and these checks do not verify its ownership. Do not use an opaque legacy credential reference: bank authentication requires the scoped encrypted vault record.
- Never paste production credentials into sandbox configuration. The vault uses authenticated encryption and keyed identity/material/component fingerprints to reject detected same-facility cross-environment reuse and reuse of revoked credential material. An already-present opposite-environment legacy bank record without component fingerprints blocks a vault save until reviewed. These checks do not establish the contents of an opaque reference, detect every reused component across different facilities, or prove concurrent cross-environment provisioning safe. Bank production vault credentials, connection tests and activation remain blocked.
- [Jenga's signature guidance](https://developer.jengahq.io/guides/get-started/generate-signature) is product-specific. Its [full-statement guide](https://developer.jengahq.io/guides/jenga-api/account-services/account-fullstatement) contains an ambiguous amount type and sample duplicate reference/transaction identifiers, and does not establish pagination or completeness. Do not infer transaction uniqueness or treat a partial response as a complete bank statement. Obtain the facility's signed specification before implementing a feed.

## Financial and safety boundaries

- A finalized invoice is distinct from a receipt, payer acknowledgement, bank transaction, refund and posted journal. Existing reviewed postings classify receivables, revenue, settlement and liabilities using selected facility accounts; balanced journals, idempotency, closed-period checks, audit and controlled reversal are enforced. Invoice posting, receipt posting and refund posting require authorized review and approved accounting policy. Prior local synthetic browser and DB tests do not establish a Safaricom receipt.
- A manual receipt or refund is a local attestation, not a verified provider transfer. Sandbox initiation/query cannot create operational receipts or journals. However, a human can still manually enter a sandbox reference as a real receipt: provenance and a separate sandbox financial ledger are unresolved. Never use operational facility data for sandbox financial experiments.
- Manual statement imports and matching can create a **reviewed import worksheet**, not a bank-confirmed feed. Insurer/SHA claim and remittance recording does not by itself prove payer payment. Trial balance, posted income statement and balance sheet reflect only available posted journals; the current invoice-balance report is not a verified as-of AR or insurer-receivables report.
- The existing journal-line guard validated account scope when a line was inserted, but did not prevent a later draft-header scope change. A rollback-only synthetic PostgreSQL probe demonstrated that changing a draft header and posting it could produce two mismatched posted lines. No real or persisted historical journal was changed by the probe. Migration `0070` prevents moving account/journal scope, revalidates active account scope on posting, and refuses to run if existing posted mismatches are detected. The accounting overview, Reporting Centre ledger views and bank worksheet fail closed on a detected posted mismatch rather than present partial totals. The Report Centre also joins account and journal scope independently. Pre-existing draft inconsistencies are not rewritten and cannot be posted until reviewed; other legacy/trigger-bypassed integrity issues and production-volume query performance remain unverified.
- Daraja's [authorization FAQ](https://developer.safaricom.co.ke/apis/Authorization) says that each new token invalidates the previous one. The current adapter obtains a fresh token for each request, with no multi-process coordination. The applicability to every facility/product needs Safaricom confirmation. Concurrent requests can invalidate an in-flight token; unknown provider dispatch must not be blindly retried. Safe bounded coordination, pool/proxy compatibility and crash/timeout tests remain work, not a solved guarantee.

## Credential and callback security

1. Payment vault records use random-IV AES-256-GCM with tenant/facility/integration-bound associated data. Keys come from server-side secret management/environment, not the frontend, Git or PostgreSQL. KCB/Jenga values are never returned by the API; forms use password inputs and clear values after save.
2. Facility administrator plus explicit permissions are required for credential/configuration changes; platform assignment is separate. Facility scopes and environment checks apply at service and database layers. Minimized configuration audit and common structured-log redaction are tested, including `Api-Key` and `merchantCode`. This is not a claim that all historical SHA/private-domain free-text audit records are secret-free.
3. Expiry, revocation and re-encryption are supported for encrypted payment credentials. The stable legacy key is also used for historical keyed identities/idempotency digests and must not be casually rotated; retain required old keys for backup recovery. Key rotation and restore procedures need operational rehearsal; rolling back a database can also restore historical revocation flags.
4. Daraja and SHA callbacks fail closed. There is no verified bank or insurer callback implementation. Before enabling any external callback, implement the provider-documented authentication, replay/idempotency controls and transaction amount, currency, reference, facility/environment and state validation. HTTP 200, a request ID or matching amount alone does not authenticate an event.
5. Require independently verified backup **and restore**, secret-manager access/recovery, deployed TLS/proxy security, least-privilege review, documented production approval, incident procedures and real facility/provider UAT before production. Test evidence below is not production certification.

## Migration and changed-file inventory

**One additive migration**, `0070_journal_facility_scope_guards.sql`, was added after the synthetic accounting defect was confirmed. It checks for unexpected guard objects and existing posted scope mismatches, locks the three ledger tables, installs scope-immutability and posting-validation triggers, and does not delete, repair, reclassify or rewrite historical data. It can block if inconsistent posted history exists; that requires controlled finance review, not bypassing the guard. It also blocks changing an existing account or journal's tenant/facility, even for a draft. Review compatibility and possible write-blocking lock duration with a tested backup/restore and an approved downtime/rollback plan before any real upgrade. Scope checks do not establish the integrity of every historic record or relation.

The isolated synthetic settlement database upgraded from 70 to **71/71** migrations. The selected before/after counts were identical: 1,248 invoices, 430 payments, 92 refunds, 312 journals, 765 journal lines, 152 accounts, 8 bank transactions, 81 integrations, 65 credential records and 9,493 audit records. A separately created, verified-empty synthetic database applied **71/71** from scratch; its historical `0002` drop ran only there. No existing database was reset or deleted. Existing vault/hub migrations `0067`/`0068` and settlement migration `0069` are unchanged. Synthetic success is not proof of production-upgrade safety. Earlier evidence and the unrelated scratch hash-drift warning are in the linked hardening report.
