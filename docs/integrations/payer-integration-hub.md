# Payer, SHA eClaims and private insurance integration hub

Status: implementation review, 28 October 2026. This guide describes the repository, not a provider certification or deployment record. No SHA, DHA, AfyaLink, Britam, PACIS or CIC sandbox connection has been verified, and none is approved for production use here.

## Boundaries and evidence

| Provider         | Registered adapter boundary                           | Available in this build                                                                                                                                         | External status                                                                                                                                  |
| ---------------- | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| SHA              | `src/integrations/sha/` and the `sha_afyalink` bridge | Facility-scoped configuration, invoice-linked local claim preparation/validation, historical records, manual advice and receipt matching; see limitations below | Application transport and callbacks are blocked. Isolated tests use mocks; draft documentation and configured credentials are not authorization. |
| Britam           | `britam_direct`                                       | Local membership, documented manual eligibility, estimated benefits, manual preauthorization/claim tracking and reconciliation                                  | No authorized provider API contract or sandbox test established.                                                                                 |
| PACIS            | `pacis_direct`                                        | Same internal/manual workflows, with its own payer configuration and policy                                                                                     | No authorized provider API contract or sandbox test established.                                                                                 |
| CIC              | `cic_direct`                                          | Explicit manual/internal registration and workflow boundary                                                                                                     | Dedicated unsupported adapter; no API contract, credentials or verified sandbox.                                                                 |
| Additional payer | `manual`                                              | SUPER_ADMIN can register a disabled, manual-only definition; explicit assignment and activation required                                                        | No electronic API implied.                                                                                                                       |

The FHIR builder and local validation are draft application code; they have **not** been certified or externally validated for conformance to the DHA guide. They are not evidence of an accepted claim.

The platform policy lists **internal workflow permissions**, not provider API capabilities. Registrations and facility activation do not mean connectivity, eligibility, coverage, approval, claim acceptance or payment. DHA HIE, AfyaLink and the eClaims FHIR draft are separate interfaces; do not substitute paths or credentials among them. Public reference material inspected:

- [SHA provider EDI](https://api-edi.provider.sha.go.ke/) — public portal; not an API contract or access grant.
- [DHA FHIR eClaims downloads](https://fhir.dha.go.ke/ig/eclaims/downloads.html) — draft FHIR R4 guide and information on requesting test access.
- [DHA HIE introduction](https://hie-docs.dha.go.ke/introduction), [billing](https://hie-docs.dha.go.ke/eclaims/billing), and [status callbacks](https://hie-docs.dha.go.ke/eclaims/status-callbacks) — HIE documentation; provider onboarding and secret provisioning are separate.
- [AfyaLink portal integration](https://afyalink.dha.go.ke/sha-portal-api-integration) — a distinct interface and onboarding process.
- [Britam medical claim process](https://ke.britam.com/help/file-a-claim/medical-insurance-claim), [PACIS provider claim form](https://www.pacisinsurance.com/wp-content/uploads/2025/08/PACIS-Insurance-Medical-Cover-Preferred-Provider-Outpatient-Claim-Form.pdf), and [CIC health insurance information](https://ke.cicinsurancegroup.com/top-questions-to-ask-before-choosing-cic-health-insurance/) establish public manual information, not facility API contracts.

## Setup and migration

1. Back up the target database and review the migration plan using `npm run db:preflight` and `npm run db:migrate:dry`. Apply the forward migrations with the project migration runner, then check `npm run db:status:all`. Reseed permissions with `npm run db:seed:permissions`. A code change or a merged PR does not deploy the app or run migrations.
2. Migration `0029_payer_integration_hub.sql` registers SHA, Britam, PACIS and CIC, internal workflow policies, facility assignments/requests and per-environment credential **references**. Existing payer configurations, claims and invoices are retained. Existing configurations are not proof of an assignment: their assignments are created disabled with `LEGACY_REVIEW_REQUIRED`. New work therefore requires platform review and facility activation.
3. In **Platform Administration → Payer registry**, a SUPER_ADMIN reviews the provider, enables its global registration, configures internal workflow policy and assigns it to an individual facility. Registering a new provider creates a disabled manual-only adapter. A platform administrator's registry access does not grant clinical or financial access to facility records.
4. In **Configuration → Payer integrations**, a facility administrator requests an unassigned payer, activates an assigned one, and may enter a provider identifier for a sandbox or production reference. Deactivation or global disablement blocks new operations; historical scoped reads remain available.
5. Reference names are generated server-side as `PAYER_HUB_T<tenantId>_F<facilityId>_<PAYER>_<SANDBOX|PRODUCTION>`. Provision credentials only in the host's approved secret-management environment; never type secrets into the application, use a browser-visible `VITE_` variable, commit them, or put real data in fixtures. A reference and presence flags are not a connection test. References are facility- and environment-specific and unique.
6. The connection-test button currently reports `NOT_TESTED`: no request is made. Production approval requests can be recorded and rejected, but approval and transport are deliberately blocked until a reviewed, facility-isolated implementation, provider authorization, security assessment and explicitly authorized sandbox verification exist.

### Permissions

Platform permissions are `payer_hub.global.read`, `payer_hub.global.manage`, `payer_hub.assign`, and `payer_hub.production.approve`; platform routes also require SUPER_ADMIN. Facility permissions are `payer_hub.catalogue.read`, `payer_hub.facility.manage`, `payer_hub.credentials.manage`, and `payer_hub.production.request`. Existing `insurance.sha.*`, `insurance.private.*`, `insurance.claims.*`, billing and `patients.read` permissions remain separately enforced. A facility-scoped account, enabled insurance module, and tenant/facility association are required; configuration permissions alone do not permit access to patient records.

## Operational workflow and safety

- Register a patient and link a real membership record to that patient and facility. Manually enter the insurer reference and evidence source when recording an actual eligibility check. Local policy information is `UNVERIFIED_LOCAL`, not payer confirmation. Unsupported adapters return unavailable/unable-to-verify, never an invented ineligibility.
- Capture approved, source-referenced facility rules and service mappings with the actual effective date, package and financial terms. Private mappings with missing fund, access point or payment mechanism are explicitly `NOT_SPECIFIED`, not verified payer terms. Calculations are estimates and not a guarantee of reimbursement or authorization. Choose real diagnoses, documentation and service codes; the application does not upload an attachment merely because a filename was typed.
- Prepare an invoice-linked claim; invoice charges and payment balances do not change. For the legacy manual claim ledger, choose an enabled registered payer and record the real external manual dispatch reference when marking submitted. The private workflow likewise records a manual dispatch reference; it does not contact the insurer.
- An explicit human-recorded payer decision is separate from submission. Record the real reference and amount; rejection requires a reason and correction/resubmission keeps history. SHA external status/eligibility, authorization, submission, remittance sync and callback registration are blocked; mock results are restricted to isolated tests. The SHA webhook returns 503 until facility-scoped verification is implemented. Some SHA manual preauthorization/status transitions still depend on the unavailable transport and are not complete alternatives to provider onboarding.
- A remittance advice alone is neither a bank confirmation nor a payment. Reconciliation does **not** post receipts or rewrite an invoice. An authorized billing user first records an independently evidenced insurer receipt, with payment method `SHA` or `Insurance - <PAYER CODE>` and the actual remittance/bank reference. The reconciliation allocation can then reference its billing payment ID. The server requires the same invoice, payer, amount and reference, locks rows and rejects duplicate receipt use across legacy, SHA and private allocations. A locally recorded receipt is still not independent bank verification. Simulated advice or SHA claims cannot be linked to real payments.
- The UI requires the receipt ID when allocating advice and can select previously imported, unallocated private advice. An API-only allocation created without a receipt remains an advice record and is not paid; there is currently no later attachment endpoint for that already-created allocation. Import advice only until the receipt is available if later matching is needed.
- Disabling, unassigning or removing an allowed workflow prevents new writes and transport calls through the hub, SHA, private, legacy claims and old DHA routes. Existing scoped records remain readable. Legacy free-text payer names can only be used for further actions when an exact unambiguous registry match exists.

## External onboarding still required

For each insurer and each facility obtain its signed provider agreement, written authorization, official versioned API/portal contract, facility/panel identifier, allowed operations, coding and tariff schedules, eligibility and preauthorization rules, support channels and callback-verification requirements. Establish an approved facility-isolated secret store and credential rotation, implement only documented endpoints with safe timeouts and idempotency, verify callbacks against facility-scoped keys, and execute expressly authorized synthetic sandbox tests. Document the evidence and any production approval before enabling an adapter. No credentials or real patient claims are sent by the current application.

## Testing

`npm run typecheck`, `npm run lint`, `npm test`, `npm run build` and `npm run build:server` are the project checks. Database-backed tests require a **disposable** PostgreSQL test database and `JALICARE_REQUIRE_DB=1`; see `src/tests/vitest/payer-hub.db.spec.ts`, `private-insurance.db.spec.ts`, and `sha-eclaims.db.spec.ts`. Their payer responses and patients are synthetic; they are not sandbox tests. See root `reportfidelis.md` for the actual results recorded for this change.
