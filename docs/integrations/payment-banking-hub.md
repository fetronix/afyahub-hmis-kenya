# Payment & Banking Integration Hub

Status: **sandbox reference implementation and administration workflow; not production-ready**. No provider sandbox or live transaction has been tested for this delivery. A mocked provider response is not an external verification.

## Repository audit and relationship to existing workflows

- `src/auth/authorization.middleware.ts`, `src/auth/scope.service.ts`, `src/db/queries.ts` and the `users`/roles/permissions tables provide authorization and tenant/facility checks. Facility-facing hub APIs reject a global SUPER_ADMIN account: a platform role alone is not facility financial authorization.
- `src/billing/payments.service.ts`, `billing_invoices` and `billing_payments` remain the source of invoice settlement and receipts. The existing settlement service locks the invoice and the existing unique transaction-code index prevents duplicate mobile-money receipts. The hub **never calls it automatically**. Staff follow the existing authorized receipt workflow; the hub can link a separately verified production transaction to an existing same-facility receipt only after explicit review.
- `src/accounting/bank-integration.service.ts` and `/api/accounting/bank/*` support independently reviewed CSV statement imports and journal-line matches. They are not a live bank feed. Hub account aliases may reference an existing same-facility `bank_accounts` row; they do not replace it or post a general-ledger journal.
- `src/components/modules/PlatformAdministrationModule.tsx`, `ConfigurationModule.tsx`, `Sidebar.tsx` and `App.tsx` host the two views and the separate finance view. Previous fake, non-persistent payment settings with example numbers and “active” claims have been replaced with the scoped hub. Existing cashier, insurance and accounting workflows are retained.
- `audit_logs` records actor, scope and safe action metadata. Provider errors and public responses do not contain provider response bodies, credentials, tokens or full account identifiers.

## Model and migration

Apply the repository's normal migration process, including additive `0028_payment_banking_hub.sql` after `0027`. The migration creates:

- `payment_provider_definitions`, `payment_provider_environments`, `payment_provider_capability_policies`: global catalogue, allowed implemented capabilities and sandbox/production availability, distinct from facility data. A policy can only restrict an adapter capability that exists in code; it cannot create a transfer capability.
- `payment_provider_assignments`, `payment_provider_access_requests`: individual facility provisioning and access requests. Facility groups are not yet implemented.
- `facility_payment_integrations`, `facility_payment_secrets`, `facility_payment_accounts`: scoped environment configuration, AES-GCM encrypted credential references and keyed fingerprints (not provider secrets), masked aliases and optional links to existing bank-account records. An alias remains `PENDING`; it is not a provider-approved account.
- `payment_hub_transactions`, `payment_hub_webhook_events`, `payment_hub_reconciliations`: scoped payment requests, untrusted notification outcomes and reviewed links to existing receipts. Composite scope foreign keys and reconciliation guards supplement service checks. Existing invoice/receipt data is not copied or deleted.

Initial provider definitions are active in the **global catalogue**, sandbox environment availability is recorded, and **no facility is assigned automatically**. Production environments are unavailable until platform policy permits requests; even a recorded approval cannot bypass the hard production-readiness gate. Revocation blocks future operations without deleting financial history. Already-dispatched requests may still be in flight and require review.

On a disposable database, apply migrations with `npm run db:migrate -- --yes`, check `npm run db:status:all`, and run `npm run db:migrate:dry`. The runner may flag destructive operations in old migrations on a brand-new empty database; review its output and do not replay historical migrations on a live database. Back up and follow the normal deployment change process before applying additive migrations to an existing installation.

## Secrets and configuration

- `PAYMENT_HUB_ENCRYPTION_KEY`: a **separate 32-byte base64 key** provisioned through the approved server secret store/environment, not committed to the repository. Generate and store it using your organization's key-management process (for example, `openssl rand -base64 32` in a secure operator environment). The hub fails closed if it is absent or malformed. AES-256-GCM uses a random IV and authenticated tenant/facility/integration context. Losing or changing the key makes stored references and idempotency digests unusable; a managed key-rotation/multi-key migration tool is **not yet implemented**. Back up the key securely and plan rotation before production.
- `PAYMENT_HUB_CALLBACK_BASE_URL`: public HTTPS application origin for the sandbox callback; no userinfo, query string or fragment. The generated endpoint is `/api/payment-hub/webhooks/mpesa`. A publicly reachable HTTPS deployment and Safaricom approval are prerequisites for any real sandbox callback test. The URL contains no secret token.
- Set normal SQL, `APP_BASE_URL`, TLS and reverse-proxy configuration as documented by the project. In production, credential configuration requires `req.secure`; configure the trusted TLS-terminating proxy correctly and do not trust arbitrary forwarded headers.
- For each Daraja integration, the facility view displays its **non-secret variable name**, `PAYMENT_HUB_T<tenantId>_F<facilityId>_I<integrationId>_<SANDBOX|PRODUCTION>`. An authorized server operator provisions that variable through the approved server environment, never through the browser, API, repository or logs. Its value is a JSON object containing five string fields: `consumerKey`, `consumerSecret`, `passkey`, `shortcode`, and `transactionType`; the latter must be the provider-approved `CustomerPayBillOnline` or `CustomerBuyGoodsOnline`. Obtain values only through the provider's secure channel; no actual or sample secrets belong in this document. Restart/reload the server as required by your deployment. The facility administrator then saves the environment reference and repeats OAuth testing. The API rejects credential values submitted in a request and returns no secrets.
- Only the scoped reference and keyed fingerprint are encrypted/stored in the database, not provider credentials. Each integration gets its own environment variable. The same Daraja consumer key cannot be configured for another integration, including another facility or environment: contractually approved shared use is not operational. On a server-secret change, the saved fingerprint no longer matches; save the reference again to invalidate prior approval and repeat the health check. For banks without a verified contract, an opaque `secret:`/`env:` reference can be recorded but is **not resolved or used**. Do not supply online-banking passwords, OTPs or real patient data in configuration.
- Platform administrators can record `env:PAYMENT_HUB_SHARED_...` references only with a contract reference and can explicitly permit a facility assignment. Shared credentials are **not resolved or used by an adapter**: provider-specific routing, contractual authorization and isolation require further implementation and testing. Facility credentials remain independent per provider and environment.

## Provisioning and approval

1. A global SUPER_ADMIN with the listed platform permissions reviews official onboarding information, activates a provider definition, enables permitted environments and implemented capability policies, and assigns selected facilities. Restricting or restoring a capability disables affected configurations and invalidates production approval; a facility must review and explicitly re-enable them. A facility may request an active, requestable provider. Disable/revoke actions are audited and take effect for future operations.
2. A facility administrator with the separate facility permissions opens **System Configuration → Payment & Banking Integrations** for the authenticated active facility. They select an available environment and implemented capabilities, coordinate facility-owned server-side credentials with the operator, save the reference, and add an alias with **only the last four digits**. Setup does not prove the provider has authorized the account.
3. For Daraja sandbox, run **Test OAuth connection**. `HEALTHY` here means only that OAuth returned an access token; it is not a claim that STK, callbacks, a bank account or merchant approval works. Enable the sandbox configuration only after adding credentials and an alias. The facility settings show the integration ID and the cashier invoice details show the invoice ID used for a sandbox request.
4. A production request requires production configuration and credentials, an alias, selected implemented capabilities and a successful sandbox OAuth check. A SUPER_ADMIN can record an approval/rejection reference after the request. **This is administrative evidence, not provider certification.** Production remains blocked in code until the actual provider contract, callback authenticity, integration tests, operations and security controls have been completed and reviewed.
5. Grant finance/cashier staff only the necessary operational permissions. No transfer operation is available. Provider registry access never confers facility finance access.

## Payment, callbacks and reconciliation

- Only `SANDBOX` Daraja initiation/query is implemented. OAuth and STK request shapes follow the cited Safaricom reference; this older source must be reconfirmed against the current provider contract. Requests are sent server-to-server, with timeout, no redirects, no logged body and no automatic retry of an ambiguous STK dispatch.
- A locally generated idempotency key binds the facility, integration, invoice, amount, phone and overpayment decision. The phone is not stored; its request digest is keyed. Reusing a key with different details is refused. A network timeout after dispatch is `UNKNOWN`; do not start a replacement request until independently reviewed. A process crash after creating an `INITIATING` record may require manual investigation.
- HTTP 200 or `ResponseCode=0` from initiation means at most **request accepted** (`PENDING`). It never changes an invoice or creates a receipt. Partial payments and explicitly approved overpayments remain governed by the existing billing settlement service.
- The public callback accepts only structurally valid outcomes for an existing, globally unique checkout ID, stores no body or phone, deduplicates stable outcome replays and limits untrusted events. It is **not authenticated** by a Safaricom signature or network rule and cannot change a payment status. It is deliberately only a hint; a forged well-formed notification is possible. Source-IP filtering or a guessed signature is not substituted for an actual provider contract. The current callback acknowledgement format and provider retry requirements require external confirmation.
- A separate authenticated server-to-server sandbox status query can report `PROVIDER_CONFIRMED` only on the implemented, conservative success shape. Unknown and nonzero results are not successes; conflicting later results become `REVIEW_REQUIRED`. This query does not establish an independently verified receipt reference or amount and does not settle a bill. A provider outage leaves the prior state unchanged.
- Reconciliation is **manual linking only**: a provider-confirmed **production** transaction, existing receipt for the same tenant/facility/invoice and exact amount, the receipt's independently verified provider reference, explicit attestation and a non-sensitive evidence reference are required. A unique active match prevents reuse of either the transaction or receipt. A correction voids the link with an audit event and does not alter the posted receipt or invoice. Sandbox records are refused. No automatic matching, new receipt creation, GL posting, multi-receipt allocation, refund or reversal is implemented.

The seed grants SUPER_ADMIN only the hub platform-management permissions and grants facility admins catalogue/settings/credential/masked-account/production-request duties; it does **not** grant them payment initiation, transaction viewing, reconciliation or transfer duties. Finance/cashier roles receive none automatically: explicitly delegate only required operational permissions.

## HTTP surface

All paths below except the callback require an authenticated session and the corresponding permission in the table above. Facility scope is resolved and validated on the server; a `facilityId` is a checked hint, never authority. All responses are `Cache-Control: no-store`.

- Platform: `GET /api/payment-hub/platform`, `GET /platform/facilities`, `POST /platform/providers`, `PATCH /platform/providers/:id`, `PUT /platform/providers/:id/environments/:environment`, `PUT /platform/providers/:id/capabilities/:capability`, `PUT /platform/providers/:id/facilities/:facilityId`, `POST /platform/integrations/:id/production-decision` (all following the `/api/payment-hub` prefix).
- Facility: `GET /api/payment-hub/facility/catalogue`, `POST /facility/providers/:id/access-request`, `POST /facility/providers/:id/integrations`, `PUT /facility/integrations/:id/credentials`, `POST /facility/integrations/:id/accounts`, `POST /facility/integrations/:id/health`, `PUT /facility/integrations/:id/enabled`, `POST /facility/integrations/:id/production-request`.
- Finance: `GET /facility/transactions`, `POST /facility/collections` (supply `Idempotency-Key`), `POST /facility/transactions/:id/query`, `POST /facility/transactions/:id/reconcile`, `POST /facility/reconciliations/:id/void`.
- Public: `POST /api/payment-hub/webhooks/mpesa` is rate limited and accepts only unverified hints. It does not create a receipt or call a provider. No other bank webhook is exposed.

## Tests, troubleshooting and go-live blockers

`src/tests/vitest/payment-hub.spec.ts` uses injected mock Daraja transport; `payment-hub.db.spec.ts` uses synthetic tenants, users, invoices, receipts and mocked network responses against disposable PostgreSQL and authenticated HTTP; `payment-hub-ui.spec.tsx` exercises separate permission-aware views. Run them with `npx vitest run src/tests/vitest/payment-hub*.spec.*` and a configured disposable database. `JALICARE_REQUIRE_DB=1` makes an unavailable DB fail rather than silently skip. Run the full project format, typecheck, lint, coverage and deployment build separately.

- `SECRET_STORE_UNCONFIGURED`: provision the separate 32-byte encryption/HMAC key server-side; never paste it into a ticket or frontend.
- `CREDENTIALS_REQUIRED` / `INVALID_CREDENTIAL_CONFIGURATION`: check that the exact facility-specific environment variable was provisioned securely with the required fields. Do not put its value in a ticket or frontend.
- `CREDENTIALS_CHANGED`: after an authorized rotation, save the environment reference again and repeat the sandbox check.
- `CREDENTIAL_ALREADY_ASSIGNED`: each integration must use an independent Daraja consumer key; shared credentials are not implemented.
- `PROVIDER_NOT_AVAILABLE`: check global lifecycle, selected environment and the exact facility assignment.
- `CAPABILITY_UNAVAILABLE` / `CAPABILITY_RESTRICTED`: the adapter or operation has not been implemented or is restricted by platform policy. Do not replace it with browser automation or online banking credentials.
- `PROVIDER_UNAVAILABLE` / `UNKNOWN`: provider connection failed, timed out or was ambiguous. Keep the original request ID, investigate through approved provider channels, and do not blindly retry.
- `PRODUCTION_BLOCKED`: expected until code, contracts, provider authorization, callback authenticity and production review are complete; recording an approval is not a bypass.
- To test an external sandbox, obtain authorized facility-specific sandbox credentials and callback access, verify the current provider contract, use only approved synthetic data, explicitly obtain permission to run the test, and record exact test evidence. No such test or provider approval is claimed in this delivery.
