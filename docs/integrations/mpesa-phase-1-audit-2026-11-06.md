Vault use and external requests are sandbox-only; production adapters are blocked. `payment-hub.db.spec.ts` exercises tenant/facility isolation with synthetic credentials and a mocked transport, not Safaricom.                                                                                                                                                                                                                                                                                                                                                                                                                                |
| OAuth and STK                        | The adapter requests a token using the selected facility's credentials, sends the documented STK parameters, and regards `ResponseCode=0` as a request acceptance only. Mocked adapter and authenticated PostgreSQL/HTTP tests exercise this; no real sandbox credential or endpoint was available in this workspace and external sandbox network access is restricted. Thus actual OAuth/STK success is **not verified**. The current adapter always uses the BusinessShortCode as PartyB, whereas Safaricom's current documentation distinguishes the till number from the business shortcode for Buy Goods.                                                                                                                                                                                                                      |
| Callbacks                            | The branch's `src/payment-hub/webhook.routes.ts` returns 503 for every delivery; no callback is authenticated or applied. Remote main's older `recordDarajaCallback` stored deduplicated **unverified** hints, not authenticated results, and also did not settle invoices. The current public Safaricom STK documentation describes callback fields but did not establish a callback-origin authentication mechanism, signature or trusted deployment contract. Amount, currency, transaction ownership and replay-safe settlement validation therefore remain unimplemented. The documented successful callback sample has amount and receipt but **no currency field**; the documented STK query response has status and IDs but **no amount, currency or receipt**. A status-only result cannot establish all required details. |
| Invoice and receipt                  | Request acceptance sets `PENDING` with no payment. A status query may mark a provider status as confirmed but explicitly does not create a receipt or change an invoice (`service.ts` `queryTransaction`). Existing `reconcileReceipt` matches an independently reviewed **existing** production receipt only; it rejects sandbox matches and does not create payments. `src/billing/payments.service.ts` separately records manual payments with invoice locking, amount checks, receipt sequence, transaction-code uniqueness, idempotency and audit in one transaction, but it is not invoked by M-Pesa callbacks.                                                                                                                                                                                                               |
| Accounting                           | No automatic M-Pesa-to-GL posting exists. `src/accounting/billing-posting.service.ts` is a separately reviewed source-linked bridge requiring explicit, scoped account selections, finalized/posted invoice and attributed receipt. `src/accounting/accounting.service.ts` checks open periods, scoped active accounts, idempotency, balanced journals and audit. The bridge starts a separate database transaction from `recordSettledPayment`, so simply chaining the two would not make receipt, invoice, journal and integration state atomic. Facility-approved settlement, receivable and liability mapping and posting policy were not supplied.                                                                                                                                                                             |
| Duplicate callbacks and retries      | Current callback replay and invalid payloads are rejected without financial changes; that is not positive callback idempotency. `payment_hub_transactions` has a scoped unique retry key, unique provider request ID and composite tenant/facility FKs (`drizzle/0028_payment_banking_hub.sql`). Initiation locks the invoice and uses a request digest; ambiguous dispatch becomes `UNKNOWN` without automatic resend. There is no provider-issued idempotency mechanism or guaranteed recovery if the process dies after Safaricom accepts a request but before its identifier is committed. Conflicting query results go to review; all non-success query results currently remain pending/unknown.                                                                                                                              |
| Reuse                                | `billing/payments.service.ts` and `billing/payment-ledger.ts` provide receipt/invoice invariants; the accounting posting bridge and `postInsideTransaction` provide reviewed, source-linked double-entry primitives. `payment_hub_reconciliations` and the bank ledger reconciliation code are review tools, not proof of external M-Pesa settlement. Refactoring them into one transaction and approving accounting classification is necessary before any automatic real posting.                                                                                                                                                                                                                                                                                                                                                 |

## Safety boundary and prerequisites

- Sandbox transactions simulate money movement and must never settle a real operational invoice or create entries indistinguishable from real receipts/ledger postings. End-to-end sandbox verification requires a clearly isolated synthetic facility/database or an explicitly designed simulation ledger; the existing operational tables do not distinguish synthetic M-Pesa receipts.
- Do not accept a guessed shared token, callback path secret, invented signature, untrusted forwarded IP, or callback payload alone as provider authentication. Obtain Safaricom's current callback-authentication/secure-channel contract and deployment controls. Confirm provider-supported verification of receipt, amount, currency and transaction ownership; the public examples alone do not establish those guarantees.
- Obtain authorized sandbox credentials in the server-side vault or deployment secret manager (never chat, browser logs or Git), a publicly reachable HTTPS callback and authorized outbound access to Safaricom, and an isolated synthetic test facility. No credentials are present in this workspace and this execution environment only permits outbound connections to a restricted host list that excludes the sandbox.
- A facility accountant must approve scoped receivable, settlement and liability accounts, posting dates, period handling and exceptional/overpayment treatment. Do not invent chart mappings or silently post to closed periods.
- Safaricom [Authorization](https://developer.safaricom.co.ke/apis/Authorization), [M-Pesa Express Simulate](https://developer.safaricom.co.ke/apis/MpesaExpressSimulate) and [Express Query](https://developer.safaricom.co.ke/apis/MpesaExpressQuery) describe official sandbox requests, acknowledgement versus completion, callback fields, explicit `1032` cancellation and distinct Buy Goods PartyB. Their examples do not grant facility approval, establish callback authentication, or prove an external test was performed.
