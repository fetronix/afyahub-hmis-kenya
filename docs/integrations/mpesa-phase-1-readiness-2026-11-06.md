# M-Pesa Phase 1 verification and Phase 2 gate

Date: 2026-11-06. Phase 1 is based on `f83ac7d552dc5008e222c4cec9f2c93d5b001546` on the designated Arena branch. The [pre-change audit](mpesa-phase-1-audit-2026-11-06.md) records inspection of remote `main` and the integration branch before implementation. This is a verification report, not a deployment authorization.

## Gate decision: NOT READY FOR PHASE 2

The real authenticated callback-to-receipt-to-ledger journey is **not implemented or verified**. `src/payment-hub/webhook.routes.ts` intentionally returns HTTP 503 for every M-Pesa callback. A status query can report a provider result but cannot authenticate callback metadata, settle an invoice, create a receipt or post a journal. Sandbox reconciliation to operational receipts is rejected. No Phase 2 bank or insurance work was started.

No actual Safaricom sandbox call, customer transaction, facility approval or production payment was performed. Sandbox access and credentials were unavailable, and this workspace's outbound allowlist excludes the Safaricom sandbox. In addition, the public STK examples inspected did not establish a provider-authenticated callback contract; the successful callback example contains amount and receipt but no currency, and the query example contains neither amount, currency nor receipt. Those omissions cannot safely be filled by guessing. Independent confirmation of what authoritative channel proves each required field is essential.

### What the successful simulation actually proves

`src/tests/integration/billing-posting.db.spec.ts`, test **“simulates a verified sandbox delivery across real billing and ledger primitives without enabling the callback”**, runs only against a synthetic PostgreSQL test database. A test double intercepts all OAuth and STK transport and a separate mock decides whether a made-up delivery is “authenticated”; neither represents a real provider protocol. Explicit fixture-only validations compare a synthetic checkout reference, facility, invoice, KES currency, amount, result and receipt code. Rejected mock authentication and altered reference, facility, invoice, amount, currency, outcome and receipt are checked before a payment is recorded.

For a synthetic KES 100 finalized invoice, the test creates a balanced, separately reviewed KES 100 invoice journal, accepts a mocked KES 20 STK request as **pending without payment**, then invokes the existing real manual billing primitive using the synthetic event. One receipt changes the balance to KES 80. It deliberately interrupts execution **after the receipt commits but before the payment journal**, observes one receipt and no payment journal, and retries twice concurrently using the same test-only durable keys. Recovery produces one receipt and one balanced KES 20 payment journal; a conflicting receipt replay is rejected. The real HTTP callback still returns 503.

This demonstrates properties of the existing billing and reviewed journal primitives under a **test-only orchestration**, not an operational callback implementation. The intermediate receipt-without-journal state proves that chaining the two current services is **not atomic**. The application has no automatic callback settlement or tested runtime recovery worker. The test-only KES assertion does not establish that Safaricom supplies or authenticates currency. No claim of provider verification, real money movement, production readiness or satisfaction of the Phase 2 gate follows from this simulation.

### Earlier regression failures and resolution

The first Phase 1 mandatory-PostgreSQL run had **2070 passed / 10 failed / 0 skipped** across 224 files. All ten failures were in `src/tests/docker-bootstrap.spec.ts`: the ordering test; the six parameterized propagation tests for `up`, `ci`, `attestation`, `run db:migrate -- --yes`, `test` and `down`; the malformed attestation test; the pre-existing Docker resources test; and the not-ready database test. Their common root cause was a **generated, untracked** `build/scripts/migrate.js` left by a prior server build. The bootstrap's safety guard correctly refuses a potentially stale built migration script before those tests reach their intended assertions. Only that generated file was removed; no database or tracked code was deleted, and the guard was not weakened. All 13 bootstrap tests passed in the focused rerun. The final full rerun is reported separately above.

The first draft of the new simulation test also failed because its test harness called `recordSettledPayment` with the wrong argument shape; the harness was corrected to use the actual service signature and all 9 billing/ledger tests passed. Earlier synthetic browser retries exposed reused mock checkout IDs colliding with the database's unique provider-reference constraint; the mock now generates a unique per-run reference, and the final browser test passed. These were synthetic setup/test issues, not evidence of a real provider outcome.

The full and parallel test logs contain nonfatal `WebSocket server error: Port 24678 is already in use` messages when multiple development-mode Vite middleware instances attempt to open their HMR listener during HTTP tests. The same message occurs in pre-Phase-1 regression logs. API assertions and the test processes passed, but this test-harness warning has not been fixed and the tests do not establish HMR behavior.

### Reproducing the checks

Use an **already provisioned, isolated synthetic PostgreSQL test database**; do not reset or reinitialize an existing database. Set the application's `SQL_HOST`, `SQL_PORT`, `SQL_DB_NAME`, `SQL_ADMIN_USER` and `SQL_ADMIN_PASSWORD` through an approved local environment/secret mechanism. Start from a clean checkout so the Docker-bootstrap safety guard is not affected by a stale generated migration bundle.

```sh
JALICARE_REQUIRE_DB=1 npx vitest run --maxWorkers=1
npm run db:status:all       # read-only journal/status check
npm run typecheck
npm run lint
npm run format:check
npm run build
npm run build:server
node scripts/check-tracked-database-backups.mjs
```

For the optional guarded browser smoke, point `CHROME_EXECUTABLE_PATH` to an available local Chromium and set `BROWSER_SMOKE_SYNTHETIC=YES`; it requires a loopback database whose name identifies it as synthetic/test and a built client and server. Run `node scripts/mpesa-phase1-browser-synthetic.mjs` only on synthetic data. The script intercepts provider traffic; it is not a Safaricom test. Any Chromium sandbox or certificate-trust bypass must be confined to the isolated test environment.

## Exact work needed before reconsidering the gate

1. Obtain authorized Safaricom sandbox access and current provider documentation for callback origin authentication/secure transport and authoritative verification of transaction identity, receipt, amount and currency. Establish a deployment with authorized outbound connectivity and a publicly reachable, reviewed HTTPS callback. Keep credentials in an approved server-side secret manager, never in chat, Git or browser-visible logs.
2. Obtain facility/provider permission and an enforceably isolated synthetic facility/database or purpose-built simulation ledger. Ensure sandbox records cannot be mistaken for real cash, receivables, receipts or journals.
3. Obtain facility-accountant approval for receivable, settlement, liability, period, attribution and exception mappings. Design and implement a reviewed callback processor that validates authenticated provenance, ownership, currency, amount, reference and state before any financial effect.
4. Implement and test one atomic transaction across callback identity, receipt, invoice and journal **or** a durable, observable, idempotent recovery process with explicit handling of every partial failure, duplicate, conflict, restart and concurrent callback. Preserve closed-period and reversal controls.
5. Run the successful and negative/replay journeys through the actual application and provider-authorized sandbox; compare provider evidence with exactly one scoped receipt, correct invoice balance and balanced posted journals. Repeat after refresh/restart and with concurrent deliveries. Preserve sanitized test evidence.
6. Resolve critical regressions; repeat mandatory-PostgreSQL regression, migrations/status, typecheck, lint, production builds, browser-to-database checks and facility UAT. Review deployment TLS, credential revocation/rotation, backup restoration and residual warnings. Only then make an explicit new Phase 2 readiness decision.
